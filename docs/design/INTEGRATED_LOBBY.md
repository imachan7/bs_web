# bs_web 統合ロビー設計メモ

- 作成日: 2026-11-08
- 状態: **未実装・検討用**（このメモ自体はコードを変更しない）
- 対象: bs_web（https://github.com/imachan7/bs_web ／ 本番 https://bs-web-battle.app）
- テーマ: マッチングの流動性を最大化しつつ、サーバー代を無料枠〜極小に収めるロビー再設計

---

## 1. 目的と優先順位

優先順位は次の順で固定する。この順序が以降のすべての判断基準になる。

1. **流動性**（対戦相手が見つかる確率と速さ）
2. **サーバー代**（無料枠に収まること。ただし流動性を犠牲にしてまで削らない）
3. 実装の単純さ・珍しさ（分散技術などのロマンは優先しない）

狙いは「サーバーをなくすこと」ではない。**「マッチングの母集団（プール）を割らずに、コストがかかる部分だけを痩せさせること」**である。

---

## 2. 現状整理（2026-11-08 時点のコード確認に基づく）

### 2.1 入口は3つあり、それぞれ別の仕組みで動いている

| 入口 | クライアント | サーバー |
|---|---|---|
| 合言葉ルーム | `join`（`public/src/main.ts` の `joinMode: "room"`） | `RoomManager.join()`。同じ roomId に2人座れば開始 |
| ランダムマッチ | `randomMatch`（`joinMode: "random"`） | `MatchQueue`（`server/src/roomManager.ts`）＋ `tryMatch()`（`server/src/index.ts`） |
| AI戦 | `startAi`（`joinMode: "ai"`） | `RoomManager.createAiRoom()`。AIが p2 に座る |

- ランダムマッチは **FIFO（先着2人）** で、レーティングや条件指定は扱わない（2026-08-23 のユーザー判断として `MatchQueue` のコメントに明記）。
- 待機列への参加・離脱は **Socket.io の接続と一体** である。切断すると `MatchQueue.remove()` で列から消え、幽霊対策として正しいが、裏返すと **「アプリ／タブを閉じた人の募集は残らない」**。
- モードは排他である。AI戦を始めると待機列から外れ、合言葉ルームに座ると待機が取り消される（`index.ts` のコメントに「両方に居させると壊れる」旨の明記あり）。つまり現状は **「待ちながら他のことをする」が構造的にできない**。

### 2.2 流動性のボトルネックは「同時性」への依存

現行ランダムマッチが成立するには、**2人が同じ数十秒〜数分の窓で待機列にいる** 必要がある。同時接続が少ないニッチなタイトルでは、この同時性が最も成立しにくい条件になる。キュー自体の実装に問題があるのではなく、前提が厳しい。

### 2.3 コストの主因はすでに特定されている

`docs/ops/DEPLOY_CLOUDRUN.md` §5 の通り、本番コストの主因は **ロビーのタブ放置**（ページを開いた瞬間に `io()` で接続し、開きっぱなしで Cloud Run インスタンスが生き続ける。1人が24時間放置すると月720時間 vs 無料枠50時間）。

対策として 2026-09-18 に「対戦していない socket の15分アイドル切断」が入ったが、**待機列・相手待ちのルームは切断対象外** とされている。つまり現状は、

> **流動性のために人を待たせるほど、接続維持コストが増える**

という構造的なジレンマを抱えている。本設計の中心は、このジレンマの解消である。

### 2.4 周辺の既存資産

- ルール判定は `shared/` をサーバー／クライアントで共有済み（将来、対戦実行をホスト側へ移す場合の前提が揃っている）。
- Discord 連携はプロジェクトの視野に既にある（`docs/design/DISCORD_ACTIVITY.md`、バグ報告の Discord Webhook 送信は「ユーザー希望・未着手」として ops ドキュメントに記載）。
- クライアントは静的バンドル＋Socket.io 接続であり、Android 化（TWA）は可能な構成。ただし現行 `public/` に PWA manifest / Service Worker は見当たらない（後述の通り、これは通知実装と同時に解消できる）。

## 3. 設計原則

1. **プールは1つ、入口は複数。** 即時キュー・掲示板・外部リンクはすべて同じ待機者集合を参照する。入口ごとに母集団を分けない。
2. **プールへの登録は「接続」ではなく「データ」として持つ。** 募集（シーク）はレコードとして保存し、成立には常時接続を要求しない。これにより §2.3 のジレンマが消える（待たせてもインスタンスは起きない）。
3. **発見・選択は中央プール、対戦実行は分離可能にする。** マッチングと対戦セッションは別コンポーネントとし、対戦側（現行 Cloud Run / 将来のホストP2P）の都合でプールを巻き込まない。
4. **Web と Android でプールを分けない。** アプリ化しても母集団は合算する。
5. **分散発見（DHT、公共リレー相乗り等）は採用しない。** 理由は §11 にまとめるが、要は「募集の永続化」「正確な待機人数表示」「プッシュでの呼び戻し」ができず、流動性で劣るため。節約額もこの規模では誤差である。

## 4. アーキテクチャ全体像

```
        Web (現行)          Android (TWA)         Discord / X
            │                    │                      │
   ┌────────┴────────────────────┴──────────────────────┴────────┐
   │ 入口A: すぐ対戦      入口B: 募集を出す      入口C: 共有リンク   │
   │ （即時マッチ）       （シーク掲示板）       （外部からの合流）  │
   └────────┬─────────────────────────────────────────────────────┘
            │  すべて同じ SeekStore への読み書き
   ┌────────▼─────────────────────────────────────────────────────┐
   │ 統合ロビープール                                              │
   │  - SeekStore   : 募集レコードの保存（TTL・状態遷移）           │
   │  - Matcher     : 自動ペアリング＋claim の調停（単一インスタンス）│
   │  - Presence    : 在席（online / away / offline）の管理         │
   │  - Notifier    : Web Push / Discord Webhook への通知          │
   └────────┬─────────────────────────────────────────────────────┘
            │  マッチ成立（roomId 発行）
   ┌────────▼─────────────────────────────────────────────────────┐
   │ 対戦セッション（当面は現行のまま）                             │
   │  Cloud Run + Socket.io、RoomManager / GameEngine / shared/   │
   │  ※ 将来ホストP2Pへ移す場合も、この境界より上は変更しない       │
   └──────────────────────────────────────────────────────────────┘
```

### 4.1 プールの実装候補

| 候補 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **A1: 現行サーバー拡張＋外部ストア** | Socket.io サーバーにシーク機能を追加し、シークの永続化だけ Firestore / Firebase RTDB の無料枠に逃がす | 変更が最小。段階導入しやすい | Cloud Run の接続維持コストは対戦・在席分として残る |
| **A2: Cloudflare Durable Object（本命）** | 単一の Lobby 用 Durable Object が SeekStore＋Matcher を担う。WebSocket Hibernation でアイドル時は課金が止まる | 待機コストほぼ0。単一インスタンスなので claim の競合調停が自明。無料枠（100k req/日級）でこの規模は十分 | 新規スタック（Workers）の導入・運用学習が要る |
| B: Firebase RTDB のみ | クライアントが直接 RTDB のキュー／シークノードを読み書きし、トランザクションで claim を確定（サーバーコードなし） | 実装が速い。無料枠で開始できる | 調停ロジックがクライアント分散になり、将来の条件追加に弱い |

推奨は **A1 で始めて A2 へ寄せる**（§10 の段階計画）。B は Phase 1 の試作を最速で回したい場合の代替。

## 5. データモデル：シーク（Seek）

統合の要は、**ランダムマッチの待機と掲示板の募集を、同じエンティティの TTL と見せ方の違いとして扱う** ことである。

### 5.1 Seek レコード

| フィールド | 内容 |
|---|---|
| `seekId` | 一意識別子 |
| `playerRef` | 端末単位の匿名ID（アカウント登録は不要とする。現行の「登録不要ですぐ遊べる」を維持） |
| `name` | 表示名（現行の名前入力を流用） |
| `deck` | 既存 `DeckSpec`（レシピ名 or カスタムデッキ）。掲示板での公開範囲は §12 の未決事項 |
| `source` | `web` / `android` / `discord` / `link`（流入の計測用。プール自体は共通） |
| `mode` | `instant`（即時：従来のランダムマッチ相当）/ `board`（掲示板：残る募集） |
| `presence` | `online`（接続中）/ `away`（切断したが通知で呼び戻し可能）/ `offline` |
| `status` | `waiting` → `claimed`（相手が確保中）→ `matched` / `expired` / `cancelled` |
| `createdAt` / `expiresAt` | TTL。初期値案：`instant` は接続が切れたら即失効、`board` は **60分**（延長可） |
| `push` | Web Push の購読情報（任意。無いシークは `away` になれず、切断＝失効） |
| `clientVersion` | 対戦互換の確認用 |

### 5.2 既存 `MatchQueue` との対応

既存コードの概念はほぼそのまま写像できる。新規発明ではなく拡張である。

| 既存（`roomManager.ts` / `index.ts`） | 統合ロビー |
|---|---|
| `MatchQueue.add()` | `SeekStore.createSeek(mode: "instant")` |
| `MatchQueue.remove(socketId)`（切断時） | `cancelSeek()` とは **分離** する。切断時は `presence` を落とすだけに変更 |
| `MatchQueue.takePair()` | `Matcher.autoPair()`（両者 `online` の最古ペアから） |
| `broadcastQueueSize()` / `matchWaiting` | プール状態の配信（待機人数＋シーク件数＋直近の成立件数） |
| `tryMatch()` の「切断済み相手を捨てて片方を戻す」処理 | claim の応答タイムアウト時の解放処理に継承 |

## 6. マッチングロジック

### 6.1 自動ペアリング（即時）

- トリガ：新規シーク作成時、presence の変化時、1分ごとのスイープ。
- ルール：`status = waiting` かつ `presence = online` のシークを **作成順（FIFO）** に2件ずつ組にする。現行の先着原則と、レーティング・条件なしという既存判断（2026-08-23）をそのまま維持する。
- 組ができたら両者に `matchFound` 相当を通知し、既存フロー通り roomId を発行して対戦セッションへ渡す。

### 6.2 Claim（掲示板）

- 閲覧者がシークを選ぶと、そのシークは原子的に `claimed` になる（二重claim防止は A2 なら単一インスタンス処理、A1/B ならストアのトランザクションで担保）。
- 投稿者へ通知し、**応答窓（初期値案：60秒）** 以内に承認／自動承認されれば成立。タイムアウトしたらシークは `waiting` に戻る（投稿者を待たせっぱなしにしない）。
- 投稿者が `online` の場合は応答窓を待たず即成立でよい。

### 6.3 掃除（ゴースト対策）

- `online` の heartbeat は30秒間隔。途絶したら `away` へ（push 購読がある場合のみ。以後は TTL まで保持し、猶予として短縮した失効（例：残り最大5分）を適用する案も §12 で検討）。
- 期限切れスイープで `expired` を確定する。現行の「幽霊が先頭に残ると空振りする」問題は、claim 時の生存確認と応答窓で吸収する。

## 7. 主要フロー

### 7.1 即時マッチ（現行ランダムマッチの置き換え）

```
プレイヤー → [すぐ対戦] → Seek(instant, online) 作成
  → 既に online の waiting がいれば即 autoPair → roomId 発行 → 対戦開始
  → いなければ待機（この間、§8 の「待ちながら他のこと」が可能）
```

### 7.2 非同期シーク（本設計の新規価値）

```
投稿者 → [募集を出す]（デッキ選択、TTL 60分）→ Seek(board) 作成
  → 投稿者はアプリを閉じてよい（presence: away、push で呼び戻し可能）
閲覧者 → 掲示板でシークを発見 → claim
  → Notifier が投稿者へ Push「対戦相手が見つかりました」
  → 投稿者がタップして復帰 → 応答窓内に承認 → roomId 発行 → 対戦開始
```

「同じ瞬間に押す」前提が外れ、**時間差のある需要同士が当たる** ようになる。これが流動性への最大の効き目を持つ変更である。

### 7.3 リンク／Discord からの合流

```
投稿者 → シーク詳細の共有リンクを発行 → X / Discord に投稿
閲覧者 → リンクを開く → そのまま claim フロー（§6.2）へ
```

リンクは「特定シークへの合流」と「掲示板への流入」の2種を用意する。Discord 側は、既存の Activity / Webhook の構想と接続できる。

## 8. 「待ちながら他のことができる」設計

流動性の実効値は「待機者数 × 平均滞在時間」で決まる。滞在時間を伸ばす最も安い方法は、待つ苦痛を消すことである。

- 待機中でも **デッキ構築・カード閲覧・AI戦** を続けてよい。ロビーには常時「待機中バー」（経過時間、キャンセルボタン）を表示する。
- マッチ成立時はモーダルで知らせ、遷移を確認してから対戦へ移る。

### 構造上の注意（最大の改修点）

現行サーバーは「1 socket = 1 つの所在（待機列 or ルーム or AI戦）」を前提に排他制御している（§2.1）。統合ロビーでは **所在（ゲームセッション）とシーク（プール登録）を別レイヤー** に分け、`playerRef` を両者の紐付けキーにする。これが本設計で最も手を入れる部分であり、Phase 分けの理由である。

- AI戦の扱い：AI戦は中断可能（破棄して対人へ移る）を原則とし、成立モーダルで明示する。AI戦の途中状態の保存・復帰は初期スコープ外とする。

## 9. 通知

| イベント | チャネル | 備考 |
|---|---|---|
| claim された | Web Push（第一候補） | Android 化（TWA）でも Web Push が使える。Service Worker 導入は TWA の前提（manifest / SW）と同時に満たせる |
| マッチ成立（即時） | 接続中なら Socket.io、切断中なら Push | 既存 `matchFound` を拡張 |
| シーク失効間近（例：残り5分） | Push（任意・頻度は最小限） | 延長導線を付ける |
| 定期開催などの集客 | Discord Webhook / コミュニティ告知 | 技術ではなく運用。§10 Phase 3 以降 |

通知基盤は「登録不要」を壊さないこと。 Push 購読は端末単位で完結し、アカウント作成を要求しない。

## 10. 段階導入計画

各 Phase は単独で出荷可能にし、効果計測を挟む。

### Phase 0：計測（先行必須）
- 現行ランダムマッチの **成立率、待機時間の分布、時間帯別の待機者数** をログから集計／新規に記録する。
- 流動性の議論を推測から実測に変える。以降の Phase の要否はこの数字で決める。

### Phase 1：掲示板（オンライン限定）
- 現行サーバー内にシーク掲示板を追加（永続化なし、TTL 30分、投稿者が online の間だけ有効）。
- ロビーUIに掲示板一覧を追加。即時キューとプールを共有する（§5 の統合をここで成立させる）。
- 目的：最小コストで「選んで当たる」導線の需要を測る。

### Phase 2：永続シーク＋通知
- SeekStore を外部ストア（A1）へ移し、切断後もシークが残るようにする。
- Service Worker＋Web Push を導入し、claim 時の呼び戻しを実装する。
- あわせて PWA manifest を整備し、Android（TWA）化の下地をここで完了させる。

### Phase 3：プールの分離と集客
- プールを Durable Object（A2）へ分離し、待機コストをほぼ0にする（Cloud Run は対戦専用に戻る）。
- リンク共有／Discord 連携、ピーク時間の表示や定期開催など、流入を増やす施策を載せる。
- 対戦実行のホストP2P化は、本メモの範囲外（別メモで、プールを残す前提で検討する）。

## 11. 採用しない案と理由

| 案 | 理由 |
|---|---|
| DHT / libp2p による完全分散の発見 | 募集の永続化・正確な待機人数・プッシュ呼び戻しができず流動性で劣る。ブラウザでは到達手段も限られる。節約額は本規模では誤差 |
| Trystero 等の公共リレー相乗り | 発見を他人の公共ネットワークに依存し、順序の公平性や可用性を制御できない。試作には使えるが本番のプールにはしない |
| 対戦プラットフォーム全面移行（Nakama 等） | マッチメーカーは得られるが常駐サーバー運用が戻り、コスト・運用負荷の面で本プロジェクトの狙いと逆行する |
| Web／Android でプール分割 | 母集団が割れて流動性が直接落ちる。プラットフォームは `source` として記録するだけにする |
| レーティング／条件マッチの導入 | 既存判断（2026-08-23、条件なしFIFO）を尊重する。条件でプールを割る施策は、待機者数が十分に増えてから再検討する |

---

## 12. 未決事項（要ユーザー判断）

1. **シークの TTL**：初期値60分でよいか。長すぎるとゴースト募集が残り、短すぎると非同期の意味が薄れる。Phase 0 の時間帯データで調整する前提でも可。
2. **claim 応答窓**：60秒でよいか。投稿者が `away` の場合のみ長くする（例：5分）案もある。
3. **掲示板でのデッキ公開範囲**：デッキ名／色を見せると選びやすいが、対戦前の情報開示になる。名前のみ・非公開も選択肢。
4. **待機中の AI 戦の中断**：対人マッチ成立時に AI 戦を破棄する原則でよいか。
5. **`away` シークの失効猶予**：切断後も TTL 満了まで残すか、短縮失効にするか。
6. **スパム対策の水準**：端末あたり有効シーク1件まで＋作成レート制限で十分か（チート対策は当面対象外という前提は維持）。

---

## 13. 成功指標

- **マッチ成立率**：待機／シーク作成 → 成立 の割合（Phase 0 で現行値を取る）
- **待機時間の中央値**：即時マッチ／シーク経由それぞれ
- **シーク経由の成立割合**：非同期化がどれだけ新規の成立を生んだか
- **時間帯別プール人数**：定期開催などの集客施策の判断材料
- **コスト**：Cloud Run のインスタンス時間と、プール基盤（ストア／DO）の使用量が無料枠に収まっているか
