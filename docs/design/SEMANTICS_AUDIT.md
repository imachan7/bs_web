# 効果文と実装の意味照合（2026-08-16 開始）

**「書いてあるのに動いていない」ではなく、「動いているが解釈が間違っている」を探す作業の記録。**

きっかけは 2026-08-16 のユーザー指摘：

> バグなしに関しては前もあったんだけど、そもそもカードの効果の解釈がミスってるってのがある。
> 動いてるけど、そもそもその挙動が間違った効果による結果の場合がある。

実際、同じ日に `SD01-028 呪われし神殿Lv2`「相手のスピリットが疲労したとき、**自分は**ドローする」が
**相手にドローさせていた**のが見つかった。typecheck も smoke も全緑のまま2日間気づかれていない。
テストは既存の実装を写すので、**解釈の誤りはテストでは絶対に見つからない**。

## 1. 道具：`npm run audit:semantics`

`scripts/check-effect-semantics.ts`。効果文（テキスト）と `effects[]` を突き合わせ、
**食い違いの候補**を軸ごとに出す。`--card BS01-104` / `--axis S4` / `--json` が使える。

| 軸 | テキスト側の根拠 | 実装側にあるべきもの |
| :-- | :-- | :-- |
| S1 | 「ターンに1回」「ゲーム中に1回」 | `oncePerTurn` などの回数制限 |
| S2 | 「〜することで」 | `cost` 系のフィールド |
| S3 | 文末が「〜できる。」 | `optional: true`（実対戦で発動確認を出す） |
| S4 | 見出しの『自分のアタックステップ』等 | `phase` / `turn` / `phaseTurn` / `step` |
| S5 | 節に出てくる数値 | `count` / `amount` などに同じ数値 |

**この道具は「候補」しか出せない**。実バグか無害かの判断は人がやる。判断の記録がこの文書。

誤検出を減らすために入れてある前処理:

- **キーワードの定型説明文を落とす**（【神速】【覚醒】等の説明文。3枚以上に現れる同一文を自動検出）
- **引用された効果文（`"…"`）を落とす**（他のスピリットに**与える**効果の本文）
- 軸ごとの**等価表現の表**（例：「ターンに1回」は `restriction:"oncePerTurnAll"` でも実装できる）

### 2.2 「無害」と判定したもの（直さない理由）

限定が無くても**結果が変わらない**もの。多くは、エンジンの構造自体がそのステップに縛っている。

| 例 | なぜ無害か |
| :-- | :-- |
| `SD01-008 雷皇龍ジークヴルム`Lv3（【激突】を配る） | 【激突】は自分がアタックしたときしか働かず、それは自分のアタックステップしか起きない |
| `BS08-012 ダークスカルデーモン` ほか | `fieldEvent` の `anySpiritAttacked` + `turn:"opponent"` で既に相手のアタック時に限られている |
| `BS09-014 闇騎士ボールス` ほか【不死】 | 【不死】の解決がコード側で `state.phase === "attack"` を要求している |
| `BS08-055 竜騎集う円卓` / `SD02-012 天の城門` | `ownLifeDamaged` / ライフ減少の直前でしか発火しない＝相手のアタック中に限られる |
| 「ブロックできない」等の `constraint` | ブロックが起きるのは相手のアタックステップだけ |

### 2.3 「誤検出」と判定したもの（道具側の限界）

17件は**見出しとエントリの対応付けの誤り**。`levels` の重なりだけで対応付けているため、
本来は別の見出し（『このスピリットのアタック時』『自分のメインステップ』等）に属するエントリを拾ってしまう。

**ここは `check-effect-gaps.ts` のカテゴリ4が既に苦労して避けた領域**（見出しとエントリの索引対応は信頼できない）。
S4 は「候補を出して人が見る」道具として使い、対応付けの精密化はやらない。

## 3. ここから確定した一般則（実装するときに守ること）

### 3.1 `fieldEvent` は**イベント対象の持ち主**が解決の主体になる

`kind:"fieldEvent"` は、疲労した／アタックしたスピリットなどイベント対象を `self` にして解決する。
**その持ち主が効果の実行者になる**ので、「相手のスピリットが〜したとき、**自分は**〜する」を
素直に書くと**相手が実行**してしまう。

→ そういうエントリには **`selfMode: "source"`**（self＝発生源、主体＝発生源の持ち主）を必ず付ける。

### 3.2 効果文が「〜できる」なら、実対戦では**発動確認を出す**

2026-08-15 に3件（封印された魔導書の対象変更／マジックの無償化／再発揮）で確定した方針を、
2026-08-16 に**全カードへ広げた**（ユーザー確認）。エントリに `optional: true` を足すだけでよい。

例外（確認を出さない）:

- **能力の付与**（「ブロックできる」「アタックできる」「対象に選べる」）。
  これは任意の発動ではなく、できることが増えるだけ
- **コストの支払い方の選択肢**（「〜することで支払うことができる」）
- **起動能力**（`kind:"activated"`）。使うこと自体が任意なので二重に聞かない

### 3.3 見出しのステップ限定は、**実装側に同じ限定が要る**とは限らない

効果の性質上そのステップでしか出番がないなら、限定を書かなくても結果は同じ（§2.2）。
ただし**BPの増減・レベルの読み替え・効果の対象変更**は、盤面の別の判定
（「BP◯以下を破壊」「Lv◯のとき」等）から**常に参照される**ので、
限定を書き忘れると他のカードの挙動まで変わる。**この3種類は必ず限定を書く**。
