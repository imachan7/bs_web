## 3. ここから確定した一般則（実装するときに守ること）

### 3.1 `fieldEvent` は**イベント対象の持ち主**が解決の主体になる

`kind:"fieldEvent"` は、疲労した／アタックしたスピリットなどイベント対象を `self` にして解決する。
**その持ち主が効果の実行者になる**ので、「相手のスピリットが〜したとき、**自分は**〜する」を
素直に書くと**相手が実行**してしまう。

→ そういうエントリには **`selfMode: "source"`**（self＝発生源、主体＝発生源の持ち主）を必ず付ける。

### 3.2 効果文が「〜できる」なら、実対戦では**発動確認を出す**

2026-08-15 に3件（封印された魔導書の対象変更／マジックの無償化／再発揮）で確定した方針を、
2026-08-16 に**全カードへ広げた**（ユーザー確認）。エントリに `optional: true` を足すだけでよい。

例外（確認を出さない）:

- **能力の付与**（「ブロックできる」「アタックできる」「対象に選べる」）。
  これは任意の発動ではなく、できることが増えるだけ
- **コストの支払い方の選択肢**（「〜することで支払うことができる」）
- **起動能力**（`kind:"activated"`）。使うこと自体が任意なので二重に聞かない

### 3.3 見出しのステップ限定は、**実装側に同じ限定が要る**とは限らない

効果の性質上そのステップでしか出番がないなら、限定を書かなくても結果は同じ（§2.2）。
ただし**BPの増減・レベルの読み替え・効果の対象変更**は、盤面の別の判定
（「BP◯以下を破壊」「Lv◯のとき」等）から**常に参照される**ので、
限定を書き忘れると他のカードの挙動まで変わる。**この3種類は必ず限定を書く**。

### 3.4 `fieldEvent` で主体が入れ替わるのは**3イベントだけ**（2026-08-17 確認）

§3.1 は「`fieldEvent` はイベント対象の持ち主が主体になる」だが、**すべての fieldEvent が危ないわけではない**。
`triggers.ts` は `selfOverride` があるときだけ `resolveAction` の主体を差し替えるので、
危ないのは「発火先の `pid` と `selfOverride.pid` が食い違いうるイベント」に限られる。
`fireFieldEventTriggers` の呼び出しを全数確認した結果:

| イベント | 主体 | 理由 |
| :-- | :-- | :-- |
| `ownBofuExhausted` | **食い違う** | `ownerPid !== bofuSourcePid` のときだけ発火する |
| `anySpiritExhausted` | **食い違う** | 疲労した側と相手側の両方に発火する |
| `anySpiritAttacked` | **食い違う** | アタックした側と相手側の両方に発火する |
| `ownSpiritExhausted` / `ownSpiritSummoned` / `ownSpiritDestroyed` / `ownSpiritReturnedToHand` / `ownSpiritBlocked` / `ownSpiritDealtLife` / `ownSeimeiLifeCharged` | 一致する | 呼び出し側が `pid` と同じ値を `selfOverride.pid` に渡している |
| 上記以外（`selfOverride` を渡さない） | 一致する | 常に発生源の持ち主で解決される |

**上の3イベントを書くときだけ、主体を意識すればよい。** 固定する印は
`selfMode:"source"` / `ownOnly:true` / `subjectSide:"own"` のどれか。
ただし次の2つは印が無くても正しい:

- `action` が**イベント対象自身に作用する**（`coreToTrashSelf`＝アタック/疲労したスピリット自身のコアを置く）
- `anySpiritAttacked` に `turn:"own"` がある（自分のターンにアタックするのは自分のスピリットだけ）。
  **疲労は自分のターンでも相手側に起きる**（【暴風】）ので `anySpiritExhausted` には使えない

### 3.5 選択者は**アクションの type に焼き込まれている**ことがある（両方向で見る）

`chooserIsTarget` を書かなくても、実装側で相手に選ばせる type がある。
代表は `discardOpponent`（「interactiveTargets 時は選択式（選択者は破棄される相手本人）」＝
`type.ts` の定義コメント。`handDeck.ts` が `tryInteractiveCardChoice(state, targetPid, …)` を呼ぶ）。
`forcedTargetPid` は選択式の再突入用の内部フィールドで、**cards.json には書かない**。

このため「相手は、相手の手札1枚を破棄する」（マッチュラ／ツクシンモア／忍者サルトベ）は
印が無くても**適合している**。

**逆に、主語が「自分は」なのにこの type を使うと食い違う。**
選択者は片方向だけでなく**両方向**で照合すること（→ §5）。

### 3.6 『自分の◯◯ステップ』は、**「ステップ開始時」と書いていなければ任意のタイミング**（2026-08-20 確認）

見出しが『自分のメインステップ』でも、それは**発揮できる時間帯**を示すだけで、
「ステップに入った瞬間に自動で発揮する」という意味ではない。

| 効果文 | 器 |
| :-- | :-- |
| 『自分のメインステップ』**ステップ開始時**、〜する | `kind:"step"` `step:"main"`（自動発揮。BS04-065機織のハーフェレシテ） |
| 『自分のメインステップ』ターンに1回、〜**できる** | `kind:"activated"` `timing:"main"`（プレイヤーが任意のタイミングで発動。BS08帝竜騎サイクル6枚） |

`kind:"step"` は**ステップ開始時に問答無用で発揮する**器なので、任意発動の効果に使うと
「メインステップに入った瞬間に強制的に発動する」ことになる（実プレイで報告されて発覚）。
`kind:"activated"` は `cost` を省略でき（追加コスト無し）、`oncePerTurn` で「ターンに1回」を表せる。
「ターンに1回」は**発生源1体ごと**に数える（同名が2体並べばそれぞれ1回使える）。

⚠️ 発動可否の判定は `RuleValidator.validateActivateAbility` と `shared/rules.activatableAbility`（UIのボタン表示）の
**2か所に同じ条件がある**。片方だけ直すと「ボタンが出るのにサーバーが弾く」ズレになる。

### 3.7 「コストを支払わずに」が無ければ、**コストは通常どおり支払う**（2026-08-20 確認）

効果による召喚・配置で免除されるのは、**効果文に明記されたものだけ**。

- 「【転召】させずに召喚できる」→ 免除されるのは**【転召】のコア支払いだけ**。召喚コストは払う
- 「ただし、『このスピリットの召喚時』効果は発揮されない」→ **この但し書きがあるカードだけ**召喚時効果を飛ばす
  （既定は発揮する。2026-08-17 に「26枚のどれにも制限が書かれていない」として発揮するよう修正されたが、
  BS08帝竜騎サイクル6枚には**書かれていた**ため、`skipOnSummon` で個別に指定する形にした）

アクション名が `summonFromHandFree` でも、`payCost: true` を付ければ通常コストを支払う。
**名前ではなく効果文に従うこと。**

### 3.8 「自分の◯◯のスピリット」には**自分自身も含まれる**（2026-08-20 確認）

除外するのは効果文に「**このスピリット以外の**」と明記があるときだけ。

`voidCoreToOther` はこの取り違えの実例。名前のとおり「self 以外」を対象にしていたが、
それが正しいのは BS01-066スタッグローブ（「このスピリット以外のスピリット1体」）だけで、
除外の記載が無い BS09-020ヤミヤンマ・BS09-023要塞蟲ラルバにも引き継がれていた。
**既定を「自身も含む」に直し、明記があるカードにだけ `excludeSelf` を付ける**形にした。

⚠️ アクション名が挙動を保証しない。名前は最初に実装したカードの都合で付いていることがあるので、
**流用するときは効果文と突き合わせる**（`summonFromHandFree` の `payCost` も同じ構図。→ §3.7）。

同じ規則で `selfBuffByExhaustFamily`（巨神機トール／紅玉の火山弾／鎧神機ヴァルハランス）も
**発生源自身を候補に含める**ようにした（2026-08-20）。「系統：「武装」を持つ自分のスピリット1体を
疲労させることで」に除外の記載が無いため。BS06-X24 鎧神機ヴァルハランスは自身が「武装」持ちなので、
回復状態でいる間は自分を疲労させてBPを倍にできる。

この軸は `npm run audit:shared` が機械的に洗う（同じ器を共有するカードで「このスピリット以外」の
記載が割れているものを出す）。判定済みは同スクリプトの `VERIFIED` に理由つきで登録してある。

### 3.11 【強襲：N】の N は「**ターン中の回復回数の上限**」（2026-08-20 ユーザー確認）

`npm run audit:semantics` の S1 が SD02-010 轟剣士レーヴェンを「『ターンに1回まで』とあるのに
回数制限の実装が無い」として挙げるが、**実装は正しい**（`CardInstance.kyoshuUsed` がターンごとの
使用回数を持ち、`refreshSelfByExhaustNexus` が上限で弾いている）。

紛らわしいのは N の意味。【強襲】の本文を展開して書いているのはレーヴェンだけで、

> Lv2･Lv3【強襲：1】『このスピリットのアタック時』
> このスピリットは、ターンに1回まで、自分のネクサス1つを疲労させることで回復できる。

と「ターンに1回まで」「ネクサス1つ」が別々に書かれているため、
**N＝疲労させるネクサスの数**とも読める。こちらの解釈だと【強襲：3】は
「ネクサス3つを疲労させて1回だけ回復」になり、現行（3回まで回復）と挙動が変わる。

**確認の結果、N は回数の上限で確定**（現行の実装のまま）。1回につき疲労させるネクサスは1つ。
影響するのは N≧2 の3枚（BS07-X28 巨人大帝アレクサンダー＝2／BS08-X34 神造巨兵オリハルコン・ゴレム＝2／
BS07-054 神凰兵フェニックス・ゴレム＝3）。

### 3.9 「◯色のスピリットとしても扱う」は**シンボルの色にも及ぶ**（2026-08-20 ユーザー確認）

`colorAs`（継続）・`tempColors`（ターン限定）で色を得た個体は、**そのシンボルを付与色のシンボルとしても数える**。
元の色を失うわけではないので、緑1シンボルの個体が白としても扱われるなら
「緑シンボル1つ」としても「白シンボル1つ」としても数える（置き換えではない）。軽減計算にも効く。

判定は `shared/rules.countSymbols` に集約してある。**フィールドのシンボルを数えるときは必ずこれを通す**：

- **ネクサスのシンボルも数える**（スピリットだけ数えて取りこぼす事故が実際にあった。
  BS04-X16機動要塞キャッスル・ゴレム「自分の青シンボル1つにつき」）
- `symbolFix` によるシンボル固定・バウンス待機中の除外・`tempExtraSymbols` の加算もここが面倒を見る

### 3.10 継続効果は**場に出た瞬間**に有効（召喚時効果より前）（2026-08-20 確認）

「このスピリットは◯色としても扱う」のような継続効果は、召喚時効果を解決する時点で既に効いている。

実装上は `refreshLevelAsOverrides` が継続分を組み直すが、これは `handleAction` の**事後フック**でしか走らない。
そのため `fireSummonSequence` の冒頭で明示的に呼んでいる（全召喚経路の合流点）。
ここが無いと、BS09-023要塞蟲ラルバをLv2で召喚しても『召喚時』の「自分の白のスピリット」に
**自分自身が数えられない**（Lv2 の colorAs が未反映のため）。

### 3.12 「このターンの間、〜すべては」は**ターン中ずっと続く継続効果**（2026-08-28 ユーザー確認）

解決した瞬間に場にいたものへ印を付けるのではなく、**そのターンの間ずっと有効な継続効果**として置く。
したがって**解決より後に場に出たスピリットにも効く**。

実装は `turnVirtualInstances`（`lendSelfThisTurn`。→ [TURN_EFFECT_SOURCES.md](./TURN_EFFECT_SOURCES.md)）に
仮想発生源として貸し出す形で書く。個体へ印を付ける形（`temp*` フィールド）にしないこと。

BS10-056 蒼天大聖モンゴクウ『召喚時』「このターンの間、自分のスピリットすべてを、
そのスピリットが持つ最高Lvとして扱う」で確認した。

### 3.13 「BPを+する効果は発揮されない」は**BPを増やす効果だけ**を止める（2026-08-28 ユーザー確認）

効果文が「BPを**+する**」と限定しているので、文字どおりに取る。止めるのは
オーラの正の値・BPバフ・自己強化など「BPを増やす効果」だけで、次の3つには**触らない**:

- BPを**下げる**効果
- 【装甲】
- 「BPのかわりにLv／コア／コストを比べる」のような**BP比較そのものの置き換え**（`battleBpAsLevel` 等）

BS10-095 俊星流れるコロッセオLv2 で確認した。

### 3.14 「内容を見ないで選ぶ」は**ランダム**（決定的簡略化をしない）（2026-08-28 ユーザー確認）

相手の手札から「内容を見ないで1枚選ぶ」は `Math.random()` でランダムに選ぶ。
**ここは既存の「プレイヤー選択の決定的簡略化」（末尾を採る等）を適用してはいけない。**
決定的にすると、相手が危ないカードを特定の位置に置くだけで回避でき、効果が別物になるため。

テストは乱数に依存しない盤面（相手の手札を全部マジックにする／全部スピリットにする等、
どれを引いても結果が同じ状態）で書くこと。BS10-058 メルクリウス・サーペントで確認した。

### 3.15 ネクサスの『このネクサスの配置時』は `trigger:"onSummon"` で書く（2026-08-28 に実バグ発覚）

### 3.16 ⚠️ **シンボルの色とカードの色は別の値**（2026-08-29 ユーザー指摘）

**カードの `colors` からシンボルの色を導いてはいけない。** シンボルの色がカードの色と違うスピリットは実在する

| 何を知りたいか | 見るもの |
| :-- | :-- |
| カードの色（軽減・「〈色〉のスピリット」の絞り込み・装甲） | `colors` ／ `instHasColor` |
| シンボルの色（ライフダメージ・コスト軽減の数え上げ） | `symbol` ／ `symbolsOverrideContinuous` |

既存の `kind:"symbolFix"`（BS08海底に眠りし古代都市）は正しく `symbol[0]` を見ている。こちらが手本。

### 4.2 「効果の重複」の点検（2026-08-17。実バグ4件）

> 灼熱の谷のように2枚あることで処理が順次行われるべきなのにそうでないものが他にもありそう

#### (a) 誘発を複数解決するループの取りこぼし（3件）

書き方の一般則は [RESUME_STACK.md §9](./RESUME_STACK.md) に書いた。

**探し方**：`state.pendingChoice` で `return`／`break` している箇所を機械的に集め、
「**ループの中か**」「**残りを再開スタックへ積んでいるか**」の2点でふるう。
20件中7件が候補に残り、うち3件が実バグだった（残りは意図的な打ち切りか誤検出）。

#### (b) OR を2エントリに分けたための二重発火（1件）

`SD01-027 溶岩の大瀑布`Lv2「**【覚醒】/【激突】を持つ**自分のスピリットが…1枚ドローする」を
`winnerKeywordFilter` 違いの2エントリで書いていたため、**両方を持つ**
`X004 龍星神ジーク・メテオヴルム`で**2枚引いていた**。
`winnerKeywordFilter` を配列（OR）にできるようにして1エントリへ統合した。

**探し方**：同一カード内で `action` が完全に一致するエントリ対を全数列挙する（18件あった）。
そのうち**両立しうる差分**を持つものだけが危ない。今回17件は無害で、内訳は:

| 差分キー | なぜ無害か |
| :-- | :-- |
| `role`（attacker/blocker） | 1回のバトルで自分はどちらか一方 |
| `levels` | レベルで排他 |
| `trigger`（onSummon / onAttack / onBlock…） | イベントが別 |
| `event`（ownMagicUsed / opponentMagicUsed…） | 同上 |
| `magicCostEquals` | 1枚のマジックのコストは1つ |
| `winnerNameContains` | 1体が両方の名前を含むことはない |

**一般則**：**キーワード・系統・色のような「1体が同時に複数持てる」フィルタで OR 分割してはいけない。**
配列（OR）を1エントリで書く。分割してよいのは上の表のように**構造的に排他**な軸だけ。

### 4.1 積み残しだった `magicTargetRedirect` の任意性（2026-08-17 解消）

**実装は最初から任意（確認式）だった。**足りなかったのは「データにそう書けないこと」。
`resolveMagic` は `magicTargetRedirect` を見つけると無条件に持ち主へ確認を出しており、
挙動としては既に「〜にできる」を満たしていた。

S3 に `BS05-040` だけが出ていた理由は**カード単位の突き合わせ**にある。
このカードは2つ目の効果が `reviveOnDestroy`（`optional` を持てる kind）なので
`canCarryOptionalEvidence` が true になり、しかしカードのどこにも `optional` が無かった。
同型の他3枚（`BS04-054` / `BS06-056` / `BS09-038`）は `optional` を持てる kind を含まないため、
**同じ実装なのに出ていなかった**（＝出ていなかったのはツールの都合で、正しさの証拠ではない）。

直し方は「型に `optional?: true` を足し、実装がそれを参照する」形にした。飾りのフィールドにしないため、
**確認を出すのは `optional:true` のときだけ**にしてある（`triggers.ts` の `isRedirectOptional`）。
現行4枚はすべて効果文が「〜にできる」なので `optional:true` を書いた＝**挙動は変わらない**。
将来「〜する」（強制）の絞り込みが出たら、`optional` を書かなければ確認なしで自動適用になる。

`OPTIONAL_CAPABLE_KINDS` にも `magicTargetRedirect` を足した（S3 は 23件 → 22件）。

**一般則**：ある軸の候補に「同型のカードのうち1枚だけ」が出ているときは、
実装の食い違いではなく**ツールの粒度**を先に疑う。カード単位で見ている軸は、
同じカードの別の効果に釣られて誤検出する。


### 接続詞（解決順）の軸は**見送った**（2026-08-17 実測）

HANDOFF §11 は次の軸として「解決順」を挙げていたが、`CONJUNCTION.md` の接続詞を
全カードの効果文で数えたところ、**照合する材料がほとんど無かった**。

| 接続詞 | 前後関係 | 該当カード |
| :-- | :-- | --: |
| 「そうしたとき」 | Aを完全解決したときだけB | **0枚** |
| 「この効果発揮後」 | 誘発の解決後にB | **0枚** |
| 「このとき」 | 同時 | 16枚 |
| 「その後」 | 前後 | 6枚 |
| 「さらに」 | 同時 | 12枚 |

前後関係と同時が**実装上いちばんはっきり分かれる**2つ（「そうしたとき」「この効果発揮後」）が
0枚なので、残る3つのために「効果文の節と `effects[]` の対応付け」を作ることになる。
これは §2.3 で S4 が断念した領域（見出しとエントリの索引対応は信頼できない）と同じ壁で、
**誤検出のほうが多くなる**。カードプールに「そうしたとき」「この効果発揮後」が入ってきたら再検討する。

### 5.1 ⚠️ このとき踏んだ落とし穴（同じ作業をする人へ）

- **公開ゾーンにカードのコピーを載せない。**手札から**移す**こと。
  コピーだと同じカードが2か所で数えられ、`BS_DEBUG_CHECKS=1` の保存則チェックが落ちる
- **既存テストが古い挙動を固定していることがある。**

  「相手が選ぶ」前提で書かれていた。選択者を直したら落ちたので、テスト側を新しい仕様に合わせた
- **`createGame(seed, …)` の seed は名前だけで、シャッフルは `Math.random()`**（`GameState.ts` の `shuffle`）。
  つまりデッキ順は実行のたびに変わり、**デッキの中身に依存するテストは間欠的に落ちる**。
