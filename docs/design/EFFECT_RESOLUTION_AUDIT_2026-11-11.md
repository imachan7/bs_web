## 2. 実バグ（確度：高）

### 2-1. BS16-007 オーガ・ドラゴン ──「オープンできる」が強制発動

- 該当: BS16-007-e1（Lv1･Lv2『このスピリットの召喚時』）
- テキスト: 「自分のデッキを上から3枚オープン**できる**。その中のバースト効果を持つカード1枚を手札に加える。残ったカードは好きな順番でデッキの下に戻す」
- 実装: `data/cards/BS16-red.json` の BS16-007-e1 が `"optional": false`。`server/src/logic/actions/revealAction.ts` の `revealOpen` ハンドラ自体に確認分岐はなく、任意性はエントリの `optional` でしか出ない（`server/src/logic/triggers.ts` は `effect.optional && state.interactiveTargets` のときだけ発動確認を出す）
- 何が起きるか: 召喚するたび確認なしに上3枚が公開され、バースト持ちがあれば強制的に手札へ入り、残りはデッキ下へ戻る。情報開示とデッキ順の変更を断れない
- 根拠:
- `SEMANTICS_AUDIT.md` §3.2 のユーザー確定方針（2026-08-16 に全カードへ拡大）「効果文が『〜できる』なら `optional: true` で発動確認を出す」
- 横断比較：「オープンできる」＋ `revealOpen` を持つ29エントリ中、`triggered` で `optional: false` なのは本カードだけ（他は全て `optional: true`）
- 同型の実バグ BSC05-020 星空の冠（`revealOpen` の強制発動）は場面検証のうえ修正済みという先例がある
- 検証方法: `npm run audit:semantics -- --card BS16-007 --axis S3` で候補に出る。現行 smoke `part366` は Lv2 の BP オーラしか見ておらず、この効果の任意性は未検証。修正時は `interactiveTargets=true` で召喚し、発動確認（`requestActivationConfirm`）が出る場面を smoke に追加して固定する
- 重大度: 中（勝敗への直接影響は限定的だが、情報公開＋手札構成の強制変更があり、方針違反が明確）

### 2-2. BS21-026 紅蟲ベニカミキラン ── 見出しのステップ限定が実装に無い

- 該当: BS21-026-e1（`fieldEvent: ownSpiritSummoned`）/ BS21-026-e2（`fieldEvent: anyBraveSummoned`）
- テキスト: Lv2『**お互いのアタックステップ**』「を持つ自分のスピリット/ブレイヴが召喚されたとき、このスピリットは回復する」
- 実装: `data/cards/BS21.json` の e1・e2 とも `phase` 指定なし。`server/src/logic/fieldEventTriggers.ts` は `effect.phase` が指定されたときだけステップで弾くため、未指定なら全ステップで発火する
- 何が起きるか: 持ちは通常召喚もできるため、メインステップで通常召喚したときにも疲労したベニカミキランが回復する（相手ターンにブロックできる状態になる等、ブロック可否に直結）
- 根拠: 同型の BS08-066-e1 / BS13-003-e1（見出しステップ限定＋ `ownSpiritSummoned` に `phase` なし）は `SEMANTICS_AUDIT.md` §2.4 で場面検証のうえ**実バグと確定し修正された**前例がある。対照例 BS19-093 ネコロン山は `phase: "main"` を明示している
- 付記: e2 は coverage で「場に出ているのに一度も適用されていない効果」5件の1つ（BS21_PLAN に「プールにのブレイヴが無いので場面を組めない」と記録あり）＝ e2 側は動作検証自体が皆無
- 検証方法: smoke `part809` の場面（`phase: "attack"` でしか検証していない）を `phase: "main"` に変え、持ちを通常召喚すると回復してしまうことを確認できる
- 重大度: 中

## 3. 要ユーザー判断の解釈論点

以下は「コードとテキストの不整合は客観的にあるが、正しい解決はルール解釈の判断が要る」もの。監査側で勝手に正解を決めていない。

### 3-1. BS20-068 腐食する大瀑布 ──「相手は〜置く」の主体と耐性判定

- テキスト: Lv2『相手のアタックステップ』「BP6000以下の相手のスピリットがアタックしたとき、**相手は**、相手のスピリットのコア1個を相手のトラッシュに置く」
- 実装: `data/cards/BS20.json` の BS20-068-e2 は `fieldEvent: anySpiritAttacked`、`subjectSide: "opponent"`、`removeCores { side: "own", to: "trash", count: 1}` で、`selfMode` の主体固定も `chooser` も無い（`audit:semantics` の S6 で唯一の残件、S7 でも重複検出）
- 論点:
1. `server/src/logic/fieldEventTriggers.ts` の `contextOf` は、対象効果では実行者をイベント対象（＝アタッカー）の持ち主に差し替える。この効果は「アタッカー自身の効果」として解決されるため、`removeCores` 側の候補絞り込み（`canTakeCoresFrom` 等）がスキップされ、**や「相手の効果を受けない」を持つスピリットからもコアを取れる**可能性がある。また実行者が対象自身になるため「相手の効果でコアを置かれたとき」系の誘発も発火しない形になる
2. 一方で同型文の repo 内正規パターン（SD01-013 冥剣士ベリト、BS19-010 スピノザンバー等の「相手は〜置く」）は、**実行者は発生源の持ち主のまま、`chooser: "owner"` で選ぶ人だけを相手にする**形で統一されている。本カードだけ流儀が違う
3. ただし `SEMANTICS_AUDIT.md` §3.18 のユーザー確認済み解釈は `destroySelf` / `exhaustSelf` についてのもので、`removeCores` 型まで定義していない
- 判断が要ること: 「相手は〜置く」型のコア除去は、(a) 発生源の効果として耐性判定を受ける（正規パターンに寄せる）のか、(b) 相手自身の行為として耐性を受けないのが正しいのか。決まれば本カードの修正と、今後同型を追加するときの一般則の両方が定まる
- 重大度: 中〜高（耐性の素通りが確定すれば対戦結果に直結する）

### 3-2. BS05-076 エターナルシールド ── デッキ破棄上限は「1回あたり」か「ターン累計」か

- テキスト: 「このターンの間、自分のデッキは…**6枚以上破棄されない**」
- 実装: `millCap { maxCount: 5}`。境界（上限5枚）自体は妥当だが、現行の `millCap` は「1回のミル呼び出しあたり」の上限でありターン累計ではない（累計版 `perTurn` は BS04 侵されざる聖域専用に別実装）
- 論点: 累計読みが正しければ、5枚ミル×2回で破れる。テキストの「このターンの間」が累計を示すかは repo 内に公式 Q の記録が無く、外部照合もしていない
- 重大度: 中低

### 3-3. 色で分割した OR エントリの二重発火 ── BS14-085 賛美するパイプオルガン / BSC05-020 星空の冠

- 両カードとも色ごとにエントリを分けており、複数色を持つスピリット（印刷多色、`colorAs` 付与）が回復すると複数エントリが発火し、破壊を複数回試行する
- BSC05-020 は repo 内で「2回目は `destroy target: "self"` で空振り、実害なし」と判定済み。ただし「破壊されない／代わりに〜」の**1回限りの代替を1回目の試行で消費した後に2回目が通る**ケースは未検証。BS14-085 は未判定
- 一般則としては `SEMANTICS_AUDIT.md` §4.2「キーワードや色のような両立しうるフィルタで OR 分割してはいけない」に反する形
- 重大度: 低〜中（代替消費のケースが実在するか次第）

### 3-4. BS14-081 神樹の切り株都市 ── §2-1 と同型の任意性欠落（確度：中）

- テキストの「オープンできる」に対し、エントリ（kind: `step`）に `optional` が無い。同型の step＋revealOpen（BS14-086-e2 / BS17-041）は `optional: true` を持つ
- 内部の `moveCards` 側で召喚自体は断れるため、実害はトップカードの公開のみ。ただしデータの不整合は明確で、§2-1 と一緒に直すのが自然
- 重大度: 低〜中

### 3-5. BS04-081 強者統べる大地 e2 ──「ターンに1回」の実装が「最初の1バトル」

- テキスト: 「指定されたスピリットは、ターンに1回、相手のスピリットにブロックされない」
- 実装: `timedEffect { duration: "battle"}`（最初に突入した1バトルにだけ効く）
- 論点: 「ターンに1回」の読みが「アタックステップ中の最初の1回限り」でよいか、「指定の持続」と分けて読むべきか
- 重大度: 低

## 6. 検出体制の穴（解釈ミスが溜まる構造的な理由）

今回の監査で一番の収穫は個別のバグよりこちらかもしれない。

1. **smoke は解釈ミスを原理的に検出できない**。50,883件全合格だが、期待値が実装の写しであるため（`SEMANTICS_AUDIT.md` 冒頭の指摘通り）。smoke が緑でも「解決が正しい」ことの証拠にはならない
2. **一番強い照合道具が休眠している**。`audit-spec-vs-data` / `validate-spec-output` / `audit:spec` は、期待値 JSON が repo 内に存在しない（`data/spec/` は `vocab.json` のみ）ため照合対象0件で実質機能していない。「効果文→期待値→データ」の全数照合が回っていない
3. **`audit:semantics` の候補157件は落ちない**。終了コードは常に0でベースライン機構が無いため、誰も見ないと候補が溜まる（同 doc §4 の警告通り今回も増えていた）。内訳: S1 回数制限 9 / S2 コスト 4 / S3 任意性 63 / S4 タイミング 30 / S5 数値 24 / S6 主体 1 / S7 選択者 12 / S8 重複 14。大半は仕分け済みの無害・誤検出だが、§2 の2件は未仕分け分から出た。あわせて「検出されなくなった VERIFIED 登録」19件の掃除警告（道具側の陳腐化）も出ている
4. **`audit:paths` の食い違い118件が未仕分け**。末尾約10件は記録マップ（`lastEmptiedSpirits` 等）のキー残留差で無害と読めたが、全件は確認できていない。この監査の本来の狙いである「解決順・再開スタック経由で発生源や主体を見失う」型（#235 の前例）が混ざっていないかは、先頭側リストの精査が要る
5. **未発火のまま残る効果がある**。coverage で「場に出ているのに一度も適用されていない効果」5件: BS21-026-e2、BS14-X02-e2、BS15-X06-e2、BS22-X06-e1、BS22-X06-e4。未発火＝場面が組まれていない＝その効果の解決は誰も見ていない、ということ

### 改善提案（本書の範囲外・次の判断材料）

- `audit:semantics` にベースライン（既知候補の固定リスト）を入れて「新規候補だけが落ちる」形にし、CI で解釈ミスの流入を止める
- spec 照合の期待値 JSON を生成する経路を復活させるか、道具自体を削除して「無い」ことを明示する（眠った道具が一番危ない）
- `audit:paths` 118件と coverage 未発火5件の仕分けを、修正 PR とは別に小さいタスクとして切る

## SP-1. 複数体破壊は「選ぶ→破壊→選ぶ→破壊」の逐次処理（確定）＋派生欠陥2件

**本体の指摘は正しい**：対話モードの destroy{count:N}（upTo 含む）は対象を選び終わってから一括破壊せず、1体選ぶ→破壊→次を選ぶ逐次処理。カースドラゴン（SD13-X01、疲労2体を破壊）で実地確認：2体目の選択提示は1体目の破壊後に来て、候補もそのたび再計算される（3→2体）。非対話も内部は1体ループだが自動選択のみで実害はなく、カウントも正しい。実サーバーは常に対話モードなので影響は実プレイ側。

対話の入口は2つとも「1体分だけ聞く」構造：upTo 型は `requestUpToChoice`（targeting.ts:347、コメントに「再開スタックには積まない」）、非 upTo 型は `tryInteractiveTargetChoice`（targeting.ts:158）＋残りを再開フレーム。この非対称から、upTo 型にだけ次の2欠陥が出る：

- **欠陥A（継続の喪失、確度：高）**：1体目の破壊時誘発が選択待ちを立てると、**残りの破壊が無言で消える**。ミケネ（破壊時回復）・兵隊アントマン（破壊時召喚）の2場面で再現（どちらも1体だけ破壊され、残りの疲労スピリットが場に残ったまま終了）。原因は upTo 型の継続が対象解決後の即時再質問（destroy.ts:245-255）だけに依存し、その条件 `!state.pendingChoice` のため誘発の選択が立っていると再質問ごと飛び、残数を持つフレームがどこにも無いこと。sequence 後段（ドロー等）は再開フレームで生き残るので、消えるのは「破壊だけ」。非 upTo 型は残りをフレームに積むため無事
- **欠陥B（「破壊した1体につき」の過少カウント、確度：高）**：割り込みゼロでも、対話ではカースドラゴンが2体破壊→**1ドロー**（非対話は2ドローで正常）。破壊記録は解決ごとに lastMoved を上書きする仕組みで、分割継続には recordAppend（追記）が必要だが、非 upTo 型の fixedCount(append=true)（destroy.ts:135）にはあるのに **upTo 型の再質問アクション（destroy.ts:251）には付いていない**ため、再入のたびに最後の1体分に上書きされる

**設計意図の確認**：同時破壊の原則自体は一次資料にある（TIMING_CHART.md ＞6・§1.5、SIMUL_DESTROY.md の destroyTargetsBatch 案A）が、対象は「対象が先に確定している集合」（destroy{all}・相打ち等）に限られ、count 型の逐次を是とする決定は文書・コメントに無い。むしろ逆の確定がある：destroy{budget}（「合計○まで好きなだけ破壊」）は **2026-08-24 のユーザー確定で「トグルで選び切ってから destroyTargetsBatch で一括破壊」** が実装済み（destroy.ts:874）で、正しい型はコードベース内にある。upTo のスキップ仕様（2026-09-28 決定）は途中停止の仕様で、欠陥A を意図したものではない。なお upTo の途中停止自体は正常動作を確認済み（スキップで止まる。壊れているのは「止めていないのに残りが消える」点と「数え方」）。

**留保**：候補プールに「入る」方向（1体目の破壊で疲労したスピリットが2体目の候補になる）は構造推論のみで実演なし（選択を挟まず自動で他を疲労させる破壊時効果がデータに無い）。ミケネの回復候補に破壊待機中の自身が含まれる件は TIMING_CHART §1.5（待機中も場にいる）と整合しうるためバグと断定しない。destroyNexus{upTo} の再質問には pendingChoice ガード自体が無く、誘発の選択を上書きする可能性が構造上ある（未実演）。
