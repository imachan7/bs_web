# 中断と再開の土台（再開スタック）

2026-08-13 起票。「効果への割り込みは、割り込まれる側がそれに対応していないといけない。
後から割り込みを持つカードが見つかったらどうするか」という問いへの設計。

**[INTERRUPTION_POINTS.md](./INTERRUPTION_POINTS.md) が「どこで聞けるか」を扱うのに対し、
この文書は「中断された側をどう書くか」を扱う。**

## 0. 方針（確定）

**割り込み点を予測しない。** 事前設計でどれだけ洗い出しても、後から割り込みを持つカードは必ず出る。
そこで「後から足すときのコストを、**割り込む側だけ書けば済む**水準まで下げる」ことを目標にする。

そのために、**割り込みの予定が無くても、順番に処理している場所は最初から再開可能に書く**。
フレーム1個のコストは小さく、後から再開可能にするコストは大きいため。

## 1. なぜ必要か（移行前の状態）

既存の割り込みは5つあり、いずれも手作りだった。1つ足すのに 3〜4ファイル・6〜23箇所を触っていた:

| 割り込み | 箇所 | 必要だったもの |
| :-- | --: | :-- |
| `magicNegate`（マジック無効化） | 23 | PendingChoice の専用フィールド＋解決分岐 |
| `magicRedirect`（対象の絞り込み） | 20 | 同上＋`magicRedirectDecision` |
| `deckMillNegate`（デッキ破棄の無効化） | 16 | 同上＋**GameState に待ち行列** |
| `reviveConfirm`（破壊の代わりに復活） | 8 | 同上＋**待ち行列** |
| `handFreeSummon`（手札からの無償召喚） | 6 | 専用フィールド |

とくに問題だったのが**深い場所から中断できない**こと。`pendingChoice.queue` は `EffectAction` の列しか
運べないため、破壊ループの中や `millDeck` の奥では中断を諦め、
`pendingReviveConfirms` / `pendingDeckMillNegates` という待ち行列へ積んで
**`handleAction` の末尾まで遅延**させていた（＝本来のタイミングからズレる）。

## 2. 骨格

`pendingChoice.queue`（`EffectAction[]`・1段・pendingChoice の内側）を、
**`GameState.resumeStack`（再開フレームの列・pendingChoice から独立）** に一般化する。

```ts
type ResumeFrame =
    | { kind: "action"; selfInstanceId: string | null; action: EffectAction; actorPid?: PlayerId }
    // 以降、段階的に追加する:
    // | { kind: "turnStart"; step: number }          … turnStartResumeStep を吸収
    // | { kind: "destroyBatch"; ids: string[]; index: number }  … 破壊ループを再開可能に
```

- **pendingChoice から独立させる**のが肝。継続が選択待ちの内側にあると、選択待ちを立てられない
  深い場所では継続も保存できない。独立していれば「フレームを積んで return」だけで中断できる
- **シリアライズ可能**（ジェネレータを使わない理由）。状態はそのまま JSON で持ち回れる

### 消化（drain）

`state.resumeStack` の**先頭から1つずつ shift して実行**し、`state.pendingChoice` が立ったら
その場で止める（残りはスタックに載ったまま）。

## 3. ⚠️ 挿入順の規則（これを間違えると解決順が壊れる）

**新しいフレームは末尾でも先頭でもなく、「今回の中断で追加された領域の末尾」に入れる。**

理由は、1回の中断で**内側の層から外側の層へ**順にフレームが積まれるため:

- 内側（例：`tryInteractiveTargetChoice` の `remainingAction`）が先に積む
- 外側（例：誘発エントリのループの残り）が後に積む
- 正しい実行順は **内側 → 外側 → それ以前の中断で積まれた古いフレーム**

したがって単純な `push`（末尾）では古いフレームより後になり、
単純な `unshift`（先頭）では内側より前に出てしまう。どちらも誤り。

実装は `GameState.resumeInsertAt` で「今回の領域の末尾」を指す:

```ts
// 中断が始まるたび（pendingChoice を立てるたび）に 0 へ戻す
state.resumeInsertAt = 0
// 積むときは今回の領域の末尾へ入れて、境界を1つ進める
state.resumeStack.splice(state.resumeInsertAt++, 0, frame)
```

移行前のコードがこの順序を**たまたま**満たしていた理由：`queue` が pendingChoice ごとに
新品（`queue: []`）だったため「今回の領域」しか存在せず、`push` がそのまま正解だった。
古いフレームと同居する `resumeStack` では成り立たないので、明示的に境界を持つ。

## 4. 後から割り込みが見つかったときの手順

1. **既存のチェックポイントに乗るか** → 乗るならカードデータのみ
2. 乗らないなら**チェックポイントを新設**する（呼び出し側1行）。
   割り込まれる側は再開可能に書いてあるので**触らない**
3. 選択の形（`kind`）が既存の `target` / `option` / `card` で足りるか →
   足りなければ UI 側の実装が要るので、着手前に chatbox で形を合意する（ここは従来どおり）

## 5. 書き忘れを検出する仕掛け

骨格を入れても「中断したのに処理を続けた」書き忘れは起こる。**静かな二重適用ではなく赤にする**:

| 仕掛け | 何を捕まえるか | 状態 |
| :-- | :-- | :-- |
| 対話モードの再実行（`npm run smoke:interactive`） | 中断・再開の経路そのものを通す。例外・再開不能・応答拒否 | **導入済み**（2026-08-13） |
| 保存則の検査（`act` のたびにカード総数の差分） | ゾーン間の移動漏れ・二重適用（`deckReveal` のデッキ流出の型） | **導入済み**（2026-08-13） |
| 中断中の盤面変更ガード | 中断した後に走り続けたコード | **導入済み**（2026-08-13。`BS_DEBUG_CHECKS=1` で有効） |

対話モードの合否は**アサーションではない**。選択結果が変わるためアサーション失敗は想定内で、
見るのは「例外なし・すべての選択待ちが解消・保存則を維持・中断ガードに引っかからない」の4つ。

### `npm run smoke:interactive` は診断用（定型には入れない）

**バッチ完了時の定型には入れない。** 選択結果が変わるためアサーション失敗が常時300件超あり、
合否の意味が定型と違う。また `createGame` がデッキをシャッフルするため
**実行ごとに件数が数件ぶれる**（自動選択の分岐が変わる）。
比較するときは件数でなく**失敗ラベルの集合**で見ること。

## 6. 手順：召喚と【転召】（2026-08-13 ユーザー確認）

```
1. 手札から召喚するカードを提示する
2. 総コストや軽減などを計算し、コストを支払う
3. 【転召】で指定された処理を行う
   ※転召対象のスピリットが効果を持つ場合、このタイミングで発揮される
   ※転召できない場合、1の前まで巻き戻す
4. カードに維持コストを置く
5. 召喚完了。その後、召喚時効果などがあれば発揮される
```

**維持コア割れによる消滅の手順**（【転召】は「コアを外す」に該当する）:

```
1. 「コアを外す／Lv維持コストを上げる」効果を発揮して解決
2. 最低維持コア未満になり消滅することになったカードは、そのままフィールドで「待機状態」になる
3. 待機状態では「フィールドを離れるとき・消滅したとき」の効果しか受け付けず、あればそれを解決
4. フィールドに残る効果があれば残り、なければ指定された場所へ移動する
```

したがって解決順は **コストの支払い → 転召 → 対象スピリットの消滅 → 召喚時効果**。

**実装上の含意**：転召の効果発揮（誘発）が選択で中断したら、
**対象の消滅はその選択が解決してから**でなければならない（§5(a) の修正はこれに基づく）。

⚠️ **未確認の食い違い**：上の手順では「4. 維持コストを置く」が「3. 転召」の**後**だが、
実装（`doSummon`）は**先に**インスタンスを作って維持コアを置き、場に出してから `resolveTensho` を呼ぶ。
転召の解決中に「自分のスピリットの数」を数える効果があると差が出うる。要確認。

### 「フィールドに残る」と「破壊したとき」の関係（2026-08-13 ユーザー確認）

**答えは接続詞で変わる。** 前提として [CONJUNCTION.md](./CONJUNCTION.md) を読むこと。

**① 別の効果として「破壊したとき〜する」がある場合 → 阻止できる**

```
効果A：破壊する
効果B：相手のスピリットを破壊したとき、〇〇する
```

**先に「フィールドに残る」を解決することで、Bの「破壊したとき」を阻止できる。**
つまり**復活した個体は「破壊された」ことにならず、Bは発揮しない**。

**② 「破壊することで」「破壊し、そうしたとき」の場合 → 阻止できない**

```
効果A：破壊する"ことで"〇〇する ／ 破壊し"そうしたとき"〇〇する
```

「ことで」「そうしたとき」は**同時発揮**なので、派生効果
（「破壊されたときフィールドに残る」など）の解決は**その後**になる。
したがって〇〇は復活の有無にかかわらず発揮される。

**⚠️ ①②はどちらも「効果による破壊」の話で、バトルのBP比較とは別**（2026-08-14 ユーザー確認）。
『BPを比べ相手のスピリットだけを破壊したとき』（`kind:"battleWon"` 35枚・`onBattleLose` 1枚）は、
**敗者が「フィールドに残る」で生き残っても発揮する**。BP比較（＞５）は破壊処理（＞６）より先に
決着しているため（[TIMING_CHART.md](./TIMING_CHART.md) §2）。

#### 実装への当てはめ

現状 `drawPerDestroyed`（BS08ドラゴンスクランブル）と `voidCoreToSelfPerDestroyed`
（X003D極帝龍騎ジーク・クリムゾン）は **`targets.length`＝「破壊しようとした数」** で数えている。
どちらのカードも効果文は「**この効果で破壊した**スピリット1体につき」なので、
①により**実際に破壊できた数**でなければならない。

`destroySpirit` の戻り値が `void` で「実際に破壊できたか」を呼び出し元が知れないのが原因。
**戻り値を用意するのが、batch 化の前にやるべき前提作業**（数え方が確定しないまま
batch 化すると、誤った数え方を固定してしまう）。

### 移行の進捗（2026-08-13）

`cause: "deplete"`（維持コア割れ）の呼び出しは**復活判定に入らない**ので対象外。
残る `cause: "destroy"` は約30箇所で、**大半が移行済み**。

**移行に使った3つの型**:

| 型 | 使いどころ | 書き方 |
| :-- | :-- | :-- |
| **A. 事前確定リスト** | 対象が先に確定するもの（`destroyAll` / 全体破壊系） | `destroyTargetsBatch(state, owner, targets, ctx)` を呼ぶだけ |
| **B. 先に選び切る** | 予算・カウントで貪欲に選ぶもの（`destroyByBpBudget` / `destroyByCostBudget` / `destroyPer` / `destroyDownToOwnCount`） | **選択だけ先に回して ID を集め**、まとめて A に渡す。貪欲な選び方は破壊そのものに依存しないので事前確定してよい |
| **C. 体数で再入** | 毎回その時点の盤面から選び直すもの（`destroy` の count ループ） | 1体ごとに処理し、中断したら `{...action, count: 残り}` を `kind:"action"` フレームで積む |

**移行しないもの（ルール②に基づく。＝これが正しい挙動）**:

`handDeck.ts` ×2 / `battleFlow.ts` ×2 / `exhaustRefresh.ts` ×1 / `destroy.ts` の
`destroyOwnByCost`・`destroyThenMillByCost` は、いずれも
**「自分の〜を破壊する“ことで”」型＝②の同時発揮**。
派生効果（フィールドに残る）の解決は恩恵の**後**なので、
**ここで中断してはいけない**（恩恵は復活の有無にかかわらず発揮される）。

### バトル解決の移行（2026-08-14 完了）

`GameEngine.ts` のバトル解決6箇所は形が他と違う。**破壊のあとに後処理が長く続く**
（勝敗誘発 →【呪撃】→ `onBattleEnd` →【光芒】→ `clearBattle`）ため、
「破壊だけ再開できればよい」他の呼び出し元と違い、**解決全体を再入可能にする必要があった**。

- `ResumeFrame` に `kind: "battleResolve"` を追加。**1ステップ＝中断しうる呼び出し1つ**として
  `runBattleStep()` の `switch`（1〜11）に割り、`driveBattleResolution()` が順に回す。
  途中で `pendingChoice` が立ったら `{...frame, step: step + 1}` を積んで抜ける
- **＞５（BP比較）の結果は `outcome` としてフレームに載せる**。＞６以降で盤面が変わっても
  勝敗は覆らない（[TIMING_CHART.md](./TIMING_CHART.md) §2）
- **破壊された個体は場から消えるので、＞６に入る直前の写しをフレームに持つ**
  （`attackerSnapshot` / `blockerSnapshot`）。`onBattleLose` の発火とログのカード名が
  破壊後にも発生源を要求するため。生存していれば実体を、していなければ写しを使う
- 相打ちは**1つの `destroyTargetsBatch` にまとめる**（＝＞６の同時破壊）。
  破壊元が対象ごとに違うので、`targets[]` の要素ごとに `context` を持てるようにした

### 同時破壊の解決順（2026-08-14 ユーザー確認）

**同時に発揮する効果はターンプレイヤーが順番を決める**（[TIMING_CHART.md](./TIMING_CHART.md) §0）。
これを「フィールドに残る」の確認に当てはめ、`destroySpiritsFrom()` が1体を処理する前に:

1. 残りの対象のうち**確認が出る候補**を `wouldAskReviveConfirm()`（副作用なしの下見）で数える
2. **2体以上なら**ターンプレイヤーに `PendingChoice.destroyOrder` で聞いて中断する
   （1体以下なら順番に意味が無いので聞かない）
3. 答えは `GameState.destroyOrderPick` に載り、再開時にその個体を残りの先頭へ入れ替える

粒度は**体ごと**（選んだ側の「残る」→「破壊されたとき」を最後まで解決してから、もう片方へ）。
バトルの相打ちに限らず `destroyAll` のような同時破壊にも同じく効く。

**未移行はゼロ**。残る非バッチ経路はすべて下の「移行しないもの」＝ルール②である。

## 8. 決着済みの判断（2026-08-13 ユーザー確認）

- **再開スタック方式を採る**（ジェネレータ化はしない）。ジェネレータは書き忘れを型で防げる利点があるが、
  `handleAction` から下の全経路を書き換える必要があり、かつ**継続がシリアライズできない**
  （プロセス再起動で解決途中のゲームが失われる）。得たい「検査されること」は
  呼び出し元にフレームを渡させる形でほぼ同じだけ得られる
- **既存5つの割り込みも新方式へ移行する**。2方式が併存すると次に触る人が古い方をコピーするため
- **復活確認・デッキ破棄無効の確認は、本来のタイミング（それが起きる瞬間）へ戻す。**
  現状は `handleAction` の末尾まで遅延している。戻すと「1体目の復活を選んだ結果、
  2体目の破壊条件が変わる」ようなケースで結果が変わるが、ルール上はそちらが正しい

## 9. ⚠️ 誘発を**複数**解決するループの書き方（2026-08-17。実バグ4件の原因）

**「ループの中で解決し、選択待ちが立ったら `return`／`break` する」は書いてはいけない。**
その時点で**同じイベントの残りの誘発が永久に失われる**。テストは全緑のまま通る
（1つ目は正しく動くので、枚数を増やさないと差が出ない）。

実際に4箇所で起きていた。どれも**同じ効果を2つ以上並べたときだけ**症状が出る:

| 関数 | 症状 |
| :-- | :-- |
| `fireStepTriggers` | 灼熱の谷2枚で破棄が1枚しか起きない |
| `fireFieldEventTriggers` | 共鳴する音叉の塔2枚で2枚目が発火しない（「〜されたとき」系すべてが該当） |
| `fireBattleWonTriggers` | バトル勝利時の誘発が2つあると2つ目が消える |
| `chooseActionMode`（`actions/control.ts`） | ヴィクトリーファイアで「スピリット1体とネクサス1つ」を選ぶとネクサスが壊れない |

### 正しい形

1. **発火するものを先に全部集める**（`firing[]`）。条件は**誘発した時点**で判定する
   （解決の途中で場が変わっても、誘発したかどうかは変わらない）
2. 集めた順に解決する。**解決の直前に発生源がまだ場に居るか確かめる**
   （先に解決した効果で破壊されうる。仮想発生源は実体が無いので在否を見ない）
3. **中断したら残りを `pushResumeFrames` で積む**

```ts
if (state.pendingChoice) {
    pushResumeFrames(state, firing.slice(i + 1).map((e) => ({ kind: "action" as const, ... })))
    return
}
```

### ⚠️ `optional`（「〜できる」）の残りは `confirmPrompt` を付ける

`kind:"action"` のフレームをそのまま積むと、**2枚目以降が確認なしで自動発動**してしまう。
`ResumeFrame` の `confirmPrompt` に確認文を入れると、再開時に**発動確認から**始まる。

### ⚠️ `fieldEvent` は self と発生源がずれる

`fieldEvent` は「self＝イベント対象／発生源＝エントリを持つカード」が別物になることがある。
フレームに `targetInstanceId` / `sourceColors` / `sourceType` を載せて解決時の文脈を保つ
（載せないと装甲やマジック効果耐性の判定が self 側から導出されて誤る）。
