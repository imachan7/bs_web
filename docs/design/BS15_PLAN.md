# BS15「覇王編 第2弾：黄金の大地」実装計画

**全90種**（コモン46 / アンコモン18 / レア12 / マスターレア8 / Xレア6）。
BS14 と同じ覇王編なので、**【バースト】が主題として続く**（機構は BS14 で実装済み。[BS14_PLAN.md](./BS14_PLAN.md) §2 が確定スキーマ）。

**⚠️ この文書は着手前の計画である。カードデータをまだ取り込んでいないため、
下の「解釈の確認」「バッチ分割」は枚数・カード名が入っていない枠だけの状態。**
データを取り込んだ時点で §2 と §4 を埋めてから実装に入ること。

## 0. 着手前に片付けるもの（BS15 より先）

弾を足すと**監査の未判定が増えて見えなくなる**。BS14 でそれが起きた
（S6・S7 が「残0件」から 12件・9件に戻り、実バグ5件が埋もれていた）。
**同じことを繰り返さないよう、BS15 を入れる前に現状の借金を減らす。**

| 借金 | 状態 | 出どころ |
| :-- | :-- | :-- |
| `coverage:effects` の実行実績0（継続効果11件） | 未着手 | HANDOFF §1 |
| `audit:semantics` S3（43件）・S4（57件）の未判定 | 未着手 | [SEMANTICS_AUDIT.md](./SEMANTICS_AUDIT.md) |
| 永久凍土の王都：自分でコストを払う4経路 | 未決（要ユーザー確認） | HANDOFF §2 |
| バトスピ Wiki との食い違い3件 | 未着手 | [RULES_BATSPI_WIKI.md](./RULES_BATSPI_WIKI.md) |

**S3・S4 は「前回無害と判定した分」と「新規」が混ざっていて区別できない**のが最大の障害。
まず判定済みを `S3_VERIFIED` / `S4_VERIFIED` に移して**新規だけが出る状態**を作る。
これをやらないと、以降どの弾でもこの2軸は使い物にならない。

## 2. 解釈の確認（**データ取り込み後・実装前にユーザーへ聞く**）

**⚠️ ここを飛ばさない。** ルールの正解はリポジトリに無い（CLAUDE.md）。
[CONJUNCTION.md](./CONJUNCTION.md) の早見表を見たうえで、次を**バッチ単位で表にして**確認する:

- 接続詞（「その後」「さらに」「このとき」）の解釈が結果を変えるカード
- 効果の解決順序・誰が割り込むか
- 複数カードに効く一般則（コスト・選択者・除去の種別）
- 印刷テキストと既存実装が食い違うもの
- 簡略化を入れるかの判断（`card-notes.json` 行き）

聞き方は「**私はこう解釈しました → これでいいですか**」。影響するカード枚数を添える。
**得た答えは `docs/design/` の手順書に1行として書く**（チャットに残すと再発見し直す）。

## 3. 新しい器が要るか

BS14 でバースト機構・`selfMode` / `subjectSide` 等は揃っている。
**まず既存の器で書けるかを確認する**。索引は次の1行で出る（型ファイルを丸読みしない）:

```
{ grep -o 'kind: "[a-zA-Z0-9_]*"' server/src/type.ts; grep -o 'type: "[a-zA-Z0-9_]*"' server/src/type.ts; } | sort -u
```

過去の実績では**1弾あたり約30種の新設アクション**が出ている（BS10:26 / BS11:26 / BS12:33 / BS13:33 / BS14:29）。
頭打ちになっていないので、BS15 でも同程度を見込む。**これが実装時間の実体**で、短縮は難しい。

## 4. バッチ分割（**2色で1エージェント**）

**⚠️ 色ごとに1体を立てない**（2026-09-13 ユーザー指示。CLAUDE.md「トークン規律」）。
コールドスタートは**エージェント数に比例**し、2色目の限界費用はほぼ実装ぶんだけ。
BS14 を4色並列で回したとき5時間制限の手前まで使い切った。

| バッチ | 担当色 | 出力先 |
| :-- | :-- | :-- |
| 1 | 赤・紫 | `data/staging/BS15-red.json` / `-purple.json` |
| 2 | 緑・白 | `data/staging/BS15-green.json` / `-white.json` |
| 3 | 黄・青 | `data/staging/BS15-yellow.json` / `-blue.json` |

委譲プロンプトに必ず入れる（CLAUDE.md「トークン規律」の全文を参照）:

- **Agent／Task ツールを使わず自分で実装すること**（再委譲の二重払い防止）
- 型4ファイルは**原則 Read 禁止**。触る1ファイルだけ、`grep -n` → `sed -n` で該当範囲のみ
- カードデータ・smoke テストも丸読みしない
- **効果節ごとの対応表を報告**（未実装の節は「未実装」と明記）
- **`{"kind":"keyword"}` を書いた時点で満足しない**（キーワードは1行目にすぎない）
- 完了条件は **`npm run typecheck` と自分が足した part の単体実行だけ**
  （2026-09-13 変更。**全 smoke と build:client はサブに回させない**。統合検証はメインループが1回）
- 最終報告は表形式で最大20行

## 5. 検証（メインループが統合後に1回）

```
npm run typecheck && npm run validate:cards && npm run validate:notes && npm run validate:gaps && npm run smoke:quiet && npm run build:client
```

弾を入れ終わったら、定型に**入れていない**次も回す:

| コマンド | 見るもの |
| :-- | :-- |
| `npm run coverage:effects` | 書いたのに一度も発火していない効果 |
| `npm run audit:choices` | 対戦者が選ぶべき場面を実装が決めていないか |
| `npm run audit:semantics` | テキストと実装の解釈違い（**S6 は精度が高い**。S7 は疑い止まり） |
| `npm run audit:parity` | クライアントが出すボタンをサーバーが拒否しないか |

`npm run gaps:update` でベースラインを縮める。意図的に実装しない札は `data/card-notes.json` に理由を書く。

## 6. 出し方

**PR は1つの作業単位で出す**（2026-09-13 ユーザー指示）。BS15 は「弾の取り込み」という
同種の作業なので**弾ごと1つの PR でよい**。ただし次は分ける:

- 取り込みの過程で見つかった**既存カードのバグ修正**
- **監査ツール・smoke の仕組み**の改良
- **インフラ・ドキュメント**

`main` へマージすると **GitHub Actions が自動で Cloud Run へデプロイする**
（2026-09-13 に設定。[DEPLOY_CLOUDRUN.md](../ops/DEPLOY_CLOUDRUN.md)）。
手で `gcloud run deploy` を打つ必要はない。**マージ＝本番反映**である点に注意。

弾が入り終わったら `data/announcements.json` に1行足す（対戦者が読む文面。内部用語を書かない）。
