## 「フィールドに残る／戻る」と『破壊時』（2026-09-08 ユーザー確認）

**「フィールドに残る」「フィールドに戻る」で場に留まったスピリット自身の『破壊時』効果は発揮する。**
これらは破壊そのものを無効にするのではなく、**破壊待機状態（§1.5）を経て、破壊で誘発された効果を
すべて処理したあと、トラッシュに置かれる代わりに場へ戻る**もの。上のコアもレベルもそのまま残り、
状態は効果文が「疲労状態で」「回復状態で」と書いていればその状態、書いていなければ元のまま。

### 破壊で誘発した効果は1つの列にまとめ、ターンプレイヤーが順番を決める（2026-09-08 ユーザー指示。実装中）

**1回の破壊で誘発するものはすべて同じ列に並べ、ターンプレイヤーが1つずつ選んで解決する。**
[RULES_BATSPI_WIKI.md](./RULES_BATSPI_WIKI.md) §1 の「解決の途中で破壊状態が解除されると、
以降の破壊条件の効果は処理されない」を満たすための形。列に入るもの:

| 列に並ぶもの | 粒度 |
| :-- | :-- |
| **破壊されたカード自身の『破壊時』効果** | **カードで1グループ**（同じカードの複数エントリはテキスト順。§0-3 の粒度の表どおり） |
| 他のカードの「〜が破壊されたとき」（`fieldEvent` の `ownSpiritDestroyed`） | 発生源のカードごとに1グループ（`pid:cardId` で分ける） |
| **「フィールドに残る／戻る」**（`reviveOnDestroy`） | 発生源ごとに1グループ |
| **【不死】**（トラッシュの【不死】持ちスピリットカード） | カードごとに1グループ。**破壊なら手段を問わず**（バトル・相手の効果・自分の効果・コストとしての破壊）列に入る。**消滅では誘発しない**（2026-10-16 ユーザー確認。以前はバッチ経由の破壊だけだった） |

**相手が持つ効果も同じ列に並び、順番を決めるのはターンプレイヤー**（§0-3）。
自分が相手のスピリットを破壊した場合、発揮するのは相手の効果だが、解決順は自分が決める。

**「フィールドに残る／戻る」が解決した時点で、その破壊は無かったことになる。**
列に残っている項目は**解決しない**（空振りする）。

### 実装の形

聞く仕組みは既にある（`resolveInOrder` の `askOrder` ＋ `resumeTriggerBatch`。
`askOrder.pid` は3箇所とも `state.turnPlayer`、`step` 版は既に両陣営の発生源を
`${持ち主名}の${カード名}` として1列に並べている）。新しく要るのは次の3つだけ。

1. **`fireFieldEventTriggers` が外部の項目を受け取れるようにする**（`extraItems`）。
   `ownSpiritDestroyed` の列に、自身の『破壊時』と「フィールドに残る」を混ぜるため
2. **内部専用アクションを2つ足す**（`cards.json` には書かない）:
   `resolveOwnDestroyTriggers`（破壊されたカード自身の『破壊時』を発揮する）と
   `applyReviveOnDestroy`（指定した `reviveOnDestroy` エントリを適用する）
3. **`action` フレームにガードを1つ足す**: `requiresPendingDestructionOf?: string`。
   この instanceId が破壊待機状態でなければ**何もしない**

⚠️ **3は「再開スタックからフレームを消す」のではなく「消化時に空振りさせる」形にすること。**
`resolveInOrder` の「残りは必ず積む」という保証は、
**積み忘れで実バグ4件（灼熱の谷が1枚しか破棄しない等）を出して作られたもの**なので穴を開けない。
フレームは積まれたまま、ガードで無効化する。

### 実装で追加で要ったもの（2026-09-08。実装しながら判明）

**4. `triggerBatch` フレームに `after`（列を使い切ったあとに実行するフレーム）を足した。**
破壊の確定（トラッシュ行き＝`destroyCommit`）を列の**あと**に置くために要る。
`resumeTriggerBatch` は1グループ解決するたびに**自分を積み直す**ので、
外側から再開スタックの固定位置に積むと追い越されて、
**誘発を1つも解決しないままトラッシュ行きが確定してしまう**（実際にそうなった）。

そもそも `suspend()` が `resumeInsertAt` を0へ戻すため、
「内側が積んでから suspend し、そのあと外側が積む」形（＝askOrder を使う誘発を
`destroySpirit` のような外側の処理が包む形）では §3 の挿入順の規則が成り立たない。
**askOrder を使う誘発を外側の処理が包むときは、外側の続きを `after` に載せること。**

**5. 内部専用アクションは `scripts/validate-cards.ts` の `INTERNAL_ONLY_ACTIONS` に理由つきで登録する。**
登録しないと「どのカードにも使われていない」で `validate:cards` が落ちる（この検査は正しい）。

### 【不死】も同じ列に入れた（2026-09-08）

**かつては「破壊そのもの」と【不死】の2択を、破壊の"外側"で別に聞いていた**
（`PendingChoice.destroyEffectOrder` ／ `GameState.destroyEffectOrderPick` ／
`ResumeFrame.destroyOne` ／ `resolveDestroyOne`）。
列に統合したのでこれらは**すべて削除した**。「残るを先に解決したら【不死】は撃てない」は、
`requiresPendingDestructionOf` のガードで**自動的に**そうなる（専用の判定が要らなくなった）。

`destroySpirit` の `deferCommit` も、`resolveDestroyOne` が唯一の利用者だったので消えた。

### 実装（2026-09-08 に直した）

**復活の判定は `commitPendingDestruction`（＝トラッシュ行きの確定地点）で行う。**
中断・再開の経路4つがすべてここを通るので、1か所で拾える。判定に要る `DestroyContext` は
破壊待機に入るときに `CardInstance.pendingDestroyContext` へ控える。

**`destroySpirit` は場に残った場合も `true` を返す**（破壊自体は成立しているため）。
「破壊したスピリット1体につき」の類はこの体数を数える。
**他のカードの「〜が破壊されたとき」（fieldEvent）も同じ列に並び、同じガードで空振りする**（2026-09-27 に追加。それまではガードが無く、「残る」の後でも発揮していた）。

**かつて `reviveOnDestroy` にあった `fireDestroyTriggerFirst` 軸は消した。**
これは「場に留める前に『破壊時』を先に発揮させる」をカード1枚（BS07-070 ブラックリチュアル）だけの
例外として書いていたもので、**その振る舞いが全カードの既定になった**ため役目を終えた。
残したままだと同じ誘発が二重に発火する。

テストは `scripts/smoke/part301.ts`。


## 0. 同時発揮の一般則（バトル以外にも効く）

2つ以上の効果が同じタイミングで同時に発揮することがある。そのときは:

1. まず **A：ゲーム中・ターン中・ステップの間、ずっと発揮し続ける効果**（継続効果）を解決する
2. 次に **B：決められたタイミングや条件で発揮する効果**を解決する
3. **A と B のそれぞれの中で複数が同時に発揮する場合は、ターンプレイヤーが解決順を決める**
4. 先に解決した効果によって新しい効果が発揮したときは、**新しく発揮した効果を先に解決する**
5. **後回しにした効果は、自分の番が来た時点の Lv でも条件（`levels`）を満たすか見直し、満たさなければ発揮しない**（公式 Q2717。2026-11-13 ユーザー決定。BS09-045 光輝の勇者皇リュートで相手を Lv1 にすれば、相手の『ブロック時』Lv2・3 は発揮しない）。見るのは Lv だけで、場にいない発生源は見直さない。実装は action フレームの `levelRecheck`（`logic/levelRecheck.ts`）

### 実装状況（2026-08-17 ユーザー確認）

**§0-3「ターンプレイヤーが解決順を決める」は、破壊だけでなく誘発でも聞くようになった**
（`step` / `fieldEvent` / `battleWon`。`GameState.resolveInOrder` の `askOrder`）。
聞く粒度は次のとおり:

| 場面 | 聞くか | 理由 |
| :-- | :-- | :-- |
| **別のカード**の効果が同時に発揮する | **聞く** | §0-3 のとおり |
| 合体スピリットのホストと合体中のブレイヴ | **聞く** | 別のカード（2026-11-14 #545。以前はブレイヴのエントリにホストの名前を付けていて同じカード扱いになり、アタック時→バトル時の固定順で解いていた） |
| 同じカードの複数エントリ | 聞かない | 「ドロー後、〜する」のようにテキストで順序が決まっている（→ [CONJUNCTION.md](./CONJUNCTION.md)）。**選択肢はカード単位でまとめ、中は元の順で解決する** |
| 同名カードを2枚以上並べた | 聞かない | 順序を入れ替えても結果が同じ（対称）。毎ステップ確認が出て煩雑になるだけ |
| 1つの効果の中のアクション列（`chooseActionMode`） | 聞かない | 同時発揮ではなく1つの効果の手順 |

実測：同時発火（2件以上）は smoke 全体で38回＝稀。聞く実装にしても対戦は煩雑にならない。

**「：フラッシュ『〜時』」の起動効果**（BS20-041・X01）：『〜時』の時間帯の中のフラッシュタイミングなら使える。『このスピリットのアタック時』＝そのアタックの間（ブロック宣言前・後のどちらでも）。『アタックステップ』など別の時間帯でも同じ読み。回数の制限が無ければ何度でも（2026-11-05 ユーザー確認）

**手札から「〜が破壊されたとき召喚できる」**（BS20-X04）は破壊誘発で、【不死】と同じくその破壊の破壊待機の列に並ぶ（2026-11-05 ユーザー確認）

**「BP0になったとき」**（BS20-041 Lv2・X05 Lv2・BS19-091）：新しく BP0 になるたびに発動し、対象はそのとき新しく BP0 になったスピリットだけ（同時に0になったものは全部）。すでに BP0 のスピリットに BP- を重ねても新しく BP0 になったとは数えない（2026-11-05 ユーザー確認）

**勝敗**：デッキ切れの敗北は「自分のスタートステップ開始時にデッキが0枚」のときだけ。0枚から引こうとしても（ドローステップ・効果のドローとも）負けにならず、引けないだけ（公式マニュアル Eternal 版 VICTORY CONDITIONS・総合ルール 1-3-2-2。2026-11-12 ユーザー確認）。ライフ0での勝敗は `lifeGate.settleLifeZero` だけが確定し、ライフを減らした経路は直後にこれを呼ぶ（呼び忘れても `handleAction` の最後の網が拾う。#437 R10）

**BPがマイナスになるとき**：BPの補正（BP+・BP-）は足し引きのまま積み上がり、実際のBP（比較・合計・表示）は0未満を0として扱う。BP3000にBP-10000なら実際のBPは0で、補正の合計は-7000のまま残る（後からBP+5000しても0、BP+8000で1000）。総合ルール 1-4-6（足し引きによる修正は負を許す）と個人サイトのQ&A（BP1000→BP-2000でBP0→BP+3000でBP2000）。2026-11-06 ユーザー確認。実装は `effectiveBp`（shared/rules/bp.ts）が合計してから0で下止めする

**召喚**：召喚したスピリットの『このスピリットの召喚時』と、ほかのカードの「（自分の）スピリットが召喚されたとき」は1つの同時発揮の列（2026-11-05 ユーザー確認・`fireSummonSequence`）。非対話では召喚時が先。召喚時の効果を書いていないカードは列に入れない（誘発しない1件で解決順を聞かないため。付与された召喚時は列の前に解決する）。smoke part772

## 1.5 ＞６「破壊処理」と**破壊待機状態**（2026-08-14 ユーザー確認）

**複数の対象は全部選んでから同時に適用する**（2026-11-12 ユーザー決定。#437 SP-1）。破壊・疲労・手札/デッキに戻すの「N体（まで）」は、1体選ぶたびに適用しない。部品は `logic/pickTargets.ts`。①耐性の確認（手札を破棄して受けない）は全員を選び終えてから1体ずつ、受けた体だけまとめて適用 ②「N体」は min(候補, N) ちょうど、「N体まで」は0〜N（スキップで確定） ③「相手は〜N体を」は相手がまとめて選ぶ ④デッキに「好きな順番で」戻すは選んだ順（最後に選んだ体が一番上。全員が対象でも聞く） ⑤非対話は選び方は自動のまま、適用はまとめて ⑥選んだ体は候補から外れる（外し直しは無い）。「好きなだけ」（`moveCards{costBudget}`）も対話では予算内を選ばせる（SP-2）。スピリットとネクサスを1つの一覧から選ぶ手札戻し（`return{nexus:"also"}`）も同じ（2026-11-13 ユーザー決定。スピリットを待機させ、ネクサスを戻してから一度に流す）


＞６は1手ではない。**破壊されたカードはすぐには場を離れない**:

```
1. スピリット／アルティメット／ネクサスは破壊されると「破壊待機状態」になる
   （＝まだフィールドにいる）

2. 『このスピリットの破壊時』「〜が破壊されたとき」等、破壊時に誘発した効果があれば発揮する
   ※ このとき、**破壊されたスピリットのシンボルも軽減シンボルに数えられる**
   ※ 派生効果の解決軸・同時発揮の順番は §0 の一般則に従う

3. 破壊待機状態のカードすべてをトラッシュに置く
   ※ 実装：同時破壊のグループ（`destroyTargetsBatch`。「すべて破壊」の効果・相打ちもここを通る）では、各体の確定を後回しにして、全員の誘発を解決し終えてからまとめて確定する（2026-11-10。設計は [SIMUL_DESTROY.md](./SIMUL_DESTROY.md)、テストは part886）
   ※ その前に、破壊待機状態の合体スピリット／合体アルティメットの
     **ブレイヴを残すかどうか**を選ぶ

4. その後、乗っていたコアをすべてリザーブへ移動させる
   ※ ブレイヴを残すことを選んだ場合は、スピリット状態になったブレイヴに、
     リザーブ／フィールドにあるコアを好きなだけ維持コストとして置く
```

### 破壊待機状態の性質

**定義**: BP比べ、または何らかの効果によってフィールドに存在するカードが破壊されている状態。

| 性質 | 内容 |
| :-- | :-- |
| 場所 | **まだフィールドに存在する** |
| コア | **カードがトラッシュに置かれるまで乗ったまま** |
| 効果の対象 | **カードの効果の影響を受ける**（対象に取れる） |
| 自分の効果 | 継続効果は発揮したまま。誘発は**破壊に関係する効果だけ**発揮できる（2026-10-30 の改訂。PENDING_STATE §1。それまでは「普通に全部働く」） |
| 疲労・回復 | **できない** |
| さらなる破壊 | 基本的に**待機状態からさらに破壊されることはない** |
| 解除されたとき | 「〜破壊されたとき、〜することで、自分のフィールドに残る／戻る」等で破壊待機状態でなくなったカードは、**破壊される前と同じ状態**でフィールドにとどまる |

### ⚠️ 効果テキストの「戻る」は**トラッシュからではない**

「疲労状態で自分のフィールドに**戻る**」の「戻る」は、**破壊待機状態から（通常の状態へ）戻る**という意味で、
トラッシュから場に出し直すことではない。**後の弾でこの記述は「残る」に変更された**（同じ意味）。

実装は当初からこの解釈で書けている（`kind:"reviveOnDestroy"` は場に留める処理で、
トラッシュからの回収ではない）。BS01〜08 の該当14枚すべてが `reviveOnDestroy` になっていることを
2026-08-14 に実データで確認済み。**新しい弾を取り込むときも「戻る」を回収と読まないこと。**

**枚数連動で複数体を戻す効果も同じ**（BS10-046 龍仙公主＝破棄したマジック1枚につき1体）。
対象は**その誘発で破壊待機状態にある個体だけ**で、トラッシュに眠る過去の破壊分は選べない
（2026-08-27 ユーザー確認）。単体が破壊された場面では、何枚破棄しても戻せるのは1体まで。

### ⚠️ 【転召】との相互作用

破壊で誘発した効果が**スピリットを召喚する**とき（例：【不死】）、
その召喚するカードが【転召】を持っていた場合、
**破壊待機状態のスピリットを【転召】の対象（生贄）にできる**。

破壊待機状態のカードはまだフィールドにいるため。手順としては
「破壊待機のスピリットのコアをすべて置く → そのスピリットは破壊待機のままトラッシュへ」となる。

### 実装状況（2026-08-14 時点）

**破壊待機状態は導入済み**。スピリット（`destroySpirit`）もネクサス（`destroyNexus`）も
「**破壊待機にする → 破壊時の誘発を解決 → カードをトラッシュへ → コアをリザーブへ**」の順で動く
（印は `CardInstance.pendingDestruction`）。誘発が選択待ちで中断しても、`ResumeFrame` の
`destroyCommit` / `destroyNexusCommit` が**待機状態のまま**残りを引き継ぐ。

| 項目 | 状態 |
| :-- | :-- |
| 誘発の解決中も場にいる（数・シンボル・効果の対象） | **対応済み** |
| コアが乗ったまま | **対応済み** |
| 待機中も誘発・継続効果が働く | **対応済み**（場にいるので走査にそのまま入る） |
| 疲労・回復できない | **対応済み**（`exhaustSpirit` / `refreshSpirit` が弾く） |
| そこからさらに破壊されない | **対応済み**（スピリット・ネクサスとも。維持コア割れも同じ） |
| 「フィールドに残る／戻る」＝待機状態の解除 | **対応済み**（スピリットは `applyRevived`、ネクサスは `reviveLastDestroyedNexus`） |
| ネクサスの破壊で誘発する効果の列 | **対応済み**（2026-11-14 ユーザー確認。#553）。「ネクサスが破壊されたとき」（両陣営）・「自分のネクサスが破壊されたとき」・「疲労させて残す」（`reviveOnDestroy{scope:"ownNexus"}`）を1つの列に並べ、ターンプレイヤーが順番を選ぶ。「残す」も「フィールドに戻す」も破壊待機の解除で、解除された後は列の残りも、破壊した側の「破壊したとき〜」（`destroyNexus` の after）も発揮しない。根拠は batspi「破壊について」（残ったら、破壊を条件とするそれ以降の効果は解決されない。ネクサスも破壊待機状態になる）。smoke part948 |
| 【転召】の生贄にできる | **対応済み**（`tenshoCandidates` は場のスピリットをそのまま見る） |
| 合体スピリットのブレイヴを残す選択 | **未対応**（ブレイヴ自体が未実装） |
| アタック・ブロックの可否 | 未対応。破壊待機中にアタック宣言は起きないので実害なし |

**この変更で挙動が変わったカード**（テストで固定済み）:

- 宝石の獣カーバルク：『破壊時』「自分のフィールドにいる系統：「想獣」1体につき」に
  **破壊された自分自身が数に入る**ようになった
- 兵隊アントマン：『破壊時』の召喚で、**自分のコアはまだ戻らず**（＝使えない）、
  一方で**自分のシンボルは軽減に数えられる**
- 盾精ラングリーズ／神鳴る霊峰：破壊されたスピリットのコアを、リザーブ経由ではなく
  **待機中の本体から直接**移すようになった
- 「破壊時に手札に戻る」（returnSelfToHand）：トラッシュからではなく
  **破壊待機状態から**手札へ移すようになった
- 戦闘獣ジャッカー：「その破壊されたネクサスを自分のフィールドに戻す」は、
  トラッシュからの再配置ではなく**破壊待機状態の解除**になった
  （＝**コアもレベルもそのまま**残る。以前は Lv1・コア0 で置き直していた）

## 1.6 **バウンス待機状態**（2026-08-16。一次資料＝バトスピ Wiki「バウンスについて」）

手札／デッキへ戻す効果（バウンス）にも待機状態がある（2020年5月のルール改定）。手順は:

1. 「手札／デッキに戻す」効果を発揮・解決する
2. 対象は「**バウンス待機状態**」となり、**フィールドに留まる**
3. 待機中に発揮できるのは「フィールドを離れるとき」「手札／デッキに戻るとき」の効果**だけ**
4. フィールドに残す効果がなければ、指定の場所（手札／デッキ上／デッキ下）へ移る

### 破壊待機状態との違い（**混同しないこと**）

| | 破壊待機（§1.5） | **バウンス待機** |
| :-- | :-- | :-- |
| シンボルを軽減に使える | ○ | **×** |
| 戻る／破壊に**無関係な効果の対象**になる | ○（数・シンボル・【転召】の生贄にも数える） | **×** |
| 発揮できる効果 | 破壊時・フィールドを離れるとき | 戻るとき・フィールドを離れるとき |

### ここから出る実装上の規則

- **1つの効果で複数体を戻すときは、全部を待機させてから一度に戻す**。
  1体ずつ戻すと、1体目の「戻ったとき」の誘発が2体目以降の対象を変えてしまう
  （実際に「コスト1以下すべてを手札に戻す」×「地竜が手札に戻ったとき相手1体を破壊」の
  組み合わせで、戻るはずだった相手が破壊されていた。smoke part194 で固定）
- 1体だけ戻す場合は待機させてすぐ戻して構わない（結果が変わらないため）
- 実装は `CardInstance.pendingBounce`。`markBounce` で待機させ、効果の解決が終わった時点で
  `flushBounces` が移動と誘発をまとめて行う（誘発が選択待ちで中断したら `bounceFlush` フレームへ）

## 1.7 **ブロックの強制は「効果」なので、装甲などで防げる**（2026-08-16。一次資料＝Wiki「激突」）

【激突】は「相手のスピリットすべては、可能ならブロックする」という**相手のスピリットを対象とした効果**。
したがって:

- **装甲で無効化できる**。相手にアタッカーの色に対する装甲を持つスピリットしかいなければ、
  ブロック強制を無視して**ライフで受けられる**
- 「相手の効果を受けない」耐性があれば当然ブロック強制も適用されない
- 「可能なら」なのでブロックできる個体がいなければ強制されない（既存どおり）

**同じ理屈で、効果によるブロック強制（`mustBlockGrant`。燃えさかる戦場／翼持つ者の空域／
ワーニングアタック）も装甲で防げる**（2026-08-16 ユーザー判断で揃えた）。

実装は `RuleValidator.hasLegalBlocker` に**強制の発生源**を渡し、`boardResistanceAgainst` で
「その効果を受けない個体」を数から外す。渡さなければ従来どおり（ブロック可否だけ）。
**それまでブロック可否しか見ておらず、装甲を素通りしていた**（ユーザー指摘で発覚。smoke part195）。

## 1.8 **アタックしていたスピリットが場を離れたら、そのアタックは終了する**（2026-08-23 ユーザー確認）

フラッシュタイミングでアタッカーがマジック等で場から取り除かれたら、**その時点でバトルが終わる**。
防御側にブロック／ライフ受けを選ばせてはいけない。

- **＞７（バトル終了宣言タイミング）は通す**。アタック宣言自体は成立しているため。
  ブロック宣言前ならバトル参加者で生き残っているものはいないので、実際に発揮されうるのは
  アタッカーの【光芒】だけ
- ⚠️ **判定は「破壊されたか」ではなく「場にいるか」で行う**。
  破壊されてもフィールドに残る効果（BS07-016 冥勇士デスカラビア等）で盤面に残ったなら、
  **そのアタックは継続する**。＞６の破壊待機状態（まだ場にいる）も同じ理由で継続し、
  確定して場を離れた時点で終了する

**それまではバトルが残り続けていた**（利用者報告で発覚）。ライフダメージ自体は
`doTakeLife` の「アタッカーが場を離れていたらダメージなし」ガードで防がれていたが、
手順としては誤りで、**アタッカーが居ないのに防御側が「ブロックする／ライフで受ける」を
選ばされる**状態だった。しかも smoke part99 に「ライフで受けてもダメージは発生しない」という
**当時の実装の写し**が仕様として書かれており、全緑をすり抜けていた。

実装は `GameEngine.endBattleIfAttackerLeftField`（handleAction の末尾。経路を問わず拾える）。
ブロック宣言後は `resolveBattle` が終了まで面倒を見るので触らない。smoke part226 / part99。

## 1.9 **ブロックされなかったアタックは「バトル」にならない**（2026-08-28 に実測で確認）

ブロック宣言が無いままライフで受けた場合、`runBattleStep` の＞６以降（バトル終了）まで進まないので、
**『このスピリットのバトル終了時』（`trigger:"onBattleEnd"`）も、そこにぶら下がるフィールドイベント
（`ownCombinedSpiritBattleEnded`）も発火しない**。効果テキストの側も「バトルしたとき」「バトル終了時」と
書いてあるので、これで一致している。

⚠️ **テストを書くときに踏む**。「アタック→ライフで受ける」だけではバトル終了時の誘発を通せないので、
`{ type: "block" }` を宣言させてから両者パスでバトルを解決させること
（`scripts/smoke/part263.ts` の BS10-086 Lv2 の実バトルケース）。

## 1.10 **指定アタック**（2026-09-06 ユーザー提供。一次資料＝Wiki「指定アタック」）

「相手のスピリット1体を指定し、そのスピリットにアタックできる」（`constraint canDirectAttack`）の手順:

| 規則 | 実装 |
| :-- | :-- |
| 指定アタックは**スピリットへのアタック**である | `battle.directedTargetInstanceId` |
| **ブロックが確定するのは、アタック時に発生する効果と【バースト】をすべて解決した後。指定先が有効なら、アタック宣言後のフラッシュ①は行わず、そのままブロック宣言（フラッシュ②へ）に移る**（2026-11-10 ユーザー確認） | 解決がすべて終わって選択待ちが無くなった時点（`handleAction` の末尾）で `resolveDirectedBlock` を通す。有効ならフラッシュ①は一度も開かない |
| 条件が無い限り**疲労状態でも指定でき、相手は疲労状態のままブロック宣言する** | `validateBlock` を経由しないので疲労チェックにかからない。宣言は正規に成立するので『ブロック時』効果も発揮する |
| 【装甲】/【重装甲】で防がれ、**指定できない** | `matchesDirectedAttackFilter` にアタッカーを渡して `boardResistanceAgainst` を通す |
| 指定先がブロック宣言前に場を離れた／条件を満たさなくなった／**アタッカーが指定アタックの効果を失った**場合は、指定アタックが無効になり**通常のアタック**になる。このとき**アタック宣言後のフラッシュタイミングは無くならない**（有効なら飛ばす、無効なら行う。2026-11-10 ユーザー確認：ブロックするはずだったスピリットがアタック時効果などで破壊されていたらフラッシュ①を行い、破壊されていなければフラッシュ①を飛ばしてブロック宣言へ） | `resolveDirectedBlock` が何もせずに抜け、フラッシュ①が開いたまま防御側の block / takeLife 待ちに落ちる |

アタッカーの『このスピリットのバトル時』は、**指定アタックではブロック確定の時点**で発揮する
（アタック宣言の時点ではまだ相手が決まっていないため。BS11-X02 の「相手の合体スピリットと
バトルしたとき」がブロッカーを見る）。通常のアタックでは従来どおりアタック宣言の時点。

## 1.11 **バトル解決の比較基準の差し替えは「ルールへの干渉」で、効果耐性では防げない**（2026-09-12 ユーザー確認）

§1.7 の裏返し。**ブロックの強制のように「スピリットを対象に取る効果」は【装甲】等で防げる**が、
**「BPのかわりにLvを比べる」のように比較基準そのものを差し替えるものはルールへの干渉**なので、
相手のスピリットが効果耐性を持っていても適用される。

| | 例 | 効果耐性で防げるか |
| :-- | :-- | :-- |
| スピリットを対象に取る効果 | ブロックの強制（【激突】）、BP修正、破壊 | **防げる**（§1.7） |
| ルールそのものへの干渉 | BS14-087 帝都アンプルール「BPのかわりにLvを比べ、Lvの低いスピリットが破壊される」 | **防げない** |

差し替え中は **BP修正（BP+X）は勝敗に影響しない**（BPを見ないため）。
比較の結果として起きる破壊は通常の破壊なので、「破壊されない」系の耐性は従来どおり効く。

## 1.12 **「バトル解決時、BPを比べずにバトルを終了させる」は、その場で終わらせない**（2026-09-27 ユーザー確認）

フラッシュで使っても、バトルは解決時（＞６）まで続き、BP の比較（とその結果の破壊）だけを飛ばす。
【呪撃】など比較によらない処理は動く。アクションは `skipBpCompare`（BS06-109・BS13-082）。
「ただちに終了」は別のアクション `endBattle`。

## 2. ここから確定した実装上の規則（2026-08-14 ユーザー確認）

- **「〜の次にアタックしたとき」は、直前のアタックがそれであること**（2026-08-27 ユーザー確認）。
  間に別のスピリットのアタックが挟まったら成立しない。アタック順を1つ記憶する実装になる
  （BS10-047 赤ずきん妖精ルージュLv3＝自分の合体スピリットの次にアタックしたとき）
- **「このターンの間、自分のライフは減らない」はあらゆる原因を止める**（2026-08-27 ユーザー確認）。
  アタックによる減少も、効果によるライフのコア除去（`lifeCrush` 系）も両方。
  対象を限る `negateLifeDamageFromTarget`（そのスピリットのアタックでは減らない）とは別物
  （BS10-093 時刻む花時計）

- **BP 比べの勝敗を条件にする誘発は、敗者の破壊待機の列（＞６-1）で解決する**（2026-11-14 ユーザー確認。#554。それまでの「敗者が残っても発揮する」を改めた）。
  勝者側の『BPを比べ相手のスピリットだけを破壊したとき』（`onBattleWin`・`kind:"battleWon"`・`ownSpiritBattleWon`・`onBattleDestroy`）も、
  敗者側の『〜に破壊されたとき』（`onBattleLose`・`ownSpiritBattleLost`＝天翼の大観覧車）も、破壊を条件とする効果なので同じ列に並ぶ。
  ターンプレイヤーが順番を選び、**解決する時点で敗者が破壊待機状態でなければ発揮しない**（「残る／戻る」を先に解決したとき）。先に解決すれば発揮する。
  「だけ」は BP 比較の結果で決まる（相打ちで片方が残っても発揮しない）。破壊後バーストは列をすべて解決した後。実装は `logic/battleOutcomeTriggers.ts`。smoke part950・part180
  - 根拠：batspi「破壊について」（残ったら、破壊を条件とするそれ以降の効果は解決されない）／天翼の大観覧車 Q22479（「BPを比べ…だけに破壊されたとき」＝バトル解決で破壊されたとき）／
    PENDING_STATE §1 例2（「相手のスピリットを破壊したとき」は破壊に関する効果で、待機状態で発揮できる）／BS18-X04 の効果文「破壊したスピリット以外の、…すべてを手札に戻す」（解決時に敗者がまだ場にいる前提の書き方）
  - **列の解決中、敗者はまだ場にいる。** 手札に戻す効果の対象に取れる（破壊待機から戻す待機へ変わり、トラッシュに置かれない）。破壊の対象にはならない（待機状態からさらに破壊されない）。
    自動選択（AI・非対話）は、ほかに候補がいれば破壊待機の体を選ばない。「破壊したスピリット以外の」は `filter.excludeBattleLoser`（BS18-X04）。
    「破壊したスピリット1体をデッキの上に戻す」（BS17-034）も通常の戻す効果で、対象を `filter.onlyBattleLoser` で敗者に絞る。
    **破壊待機の体が手札・デッキに戻されたら、通常の戻す待機（`markBounce` → `flushBounces`）に乗って場を離れる。** 破壊待機でなくなるので、同じ列の残りの破壊誘発は発揮せず、
    トラッシュに置かれないので破壊後バーストも無い（PENDING_STATE §1「別の待機状態になったら、前の待機状態で誘発する効果は解決できない」）。
    **カードごとの特例（確定時の行き先の差し替えなど）を作らず、戻す・消滅などの通常の経路に乗せること**（2026-11-14 ユーザー指示）
  - **待機状態のカードは、破壊に関係する効果以外を発揮できない**（PENDING_STATE §1）。`fireFieldEventTriggers` が、破壊待機の発生源を破壊・勝敗のイベント以外で外す（part699 R6）
- **敗者の『バトル時』BPを比べ相手のスピリットに破壊されたとき（`onBattleLose`）は＞６-1 の破壊待機の列の1件**（2026-11-05 ユーザー確認）。
  『破壊時』と同時発揮で、合体中のブレイヴの【合体時】・付与された誘発も含む（`DestroyContext.battleLoser`）。
  列に「自身の『破壊時』」を積むかの判定も、合体中のブレイヴと付与された誘発を見る（以前はホストのカードだけで、マタドーラが発揮しなかった）。smoke part777
- **【呪撃】・【光芒】は＞７**。＞６で「フィールドに残る」を使って生き残った個体は、
  ＞７の時点でまだフィールドにいる＝**【呪撃】の対象になる**
- **「バトル終了後に破壊する」も＞７**（2026-08-16 ユーザー確認。BS01-104 千本槍の古戦場Lv2）。
  【呪撃】と同じ位置で、実装も同じ場所（`runBattleStep` の＞７）に置いてある。
  効果の**発揮（コストの支払い）はブロック宣言の時点**で、破壊だけがここまで遅れる。したがって:
  - 支払いでネクサスの**レベルが下がっても破壊は実行される**（発揮は成立済み）
  - 対象が＞６で既に破壊されていれば**空振りする**（【呪撃】と同じ）
  - **装甲・効果耐性は＞７のその時点で判定する**（予約時ではない）

  器は `BattleState.endBattleDestroy`（予約リスト）＋ action `destroyBlockerAfterBattle`。
  予約時の色と種別を控えるのは、発生源が場を離れても装甲判定ができるようにするため
  - 「バトル解決時、〜を、バトル終了時に破壊する」（BS23-042）は、対象の条件（Lv など）をバトル解決時に判定して予約し、その後に発生源が場を離れても破壊する（2026-11-09 ユーザー確認。器は `destroyBlockerAtBattleEnd`）
- **相打ち（同BP）は＞６の同時破壊**。「フィールドに残る」と「破壊されたとき」は同じステップなので、
  §0-3 により **ターンプレイヤーが「どちらのスピリットから破壊処理をするか」を選ぶ**。
  粒度は**体ごと**（選んだ側の「残る」→「破壊されたとき」を最後まで解決してから、もう片方へ）
- 上の「ターンプレイヤーが順番を決める」は**バトルに限らない**。`destroyAll` のような同時破壊でも、
  「フィールドに残る」の確認が**2体以上**に出るなら、その都度ターンプレイヤーに順番を聞く
- **「〜の自分のスピリットすべては、破壊されたとき、残る（戻る・残ることができる）」は、同時に破壊された体それぞれに効く**（体ごとに選べる。データは `perDestroyed: true`。2026-11-10 ユーザー決定・暫定：公式Q&Aに複数体の裁定が無いため。下の Q22359 は「そのスピリットを残す」型）
- **「〜が破壊されたとき」は、2体以上が同時に破壊されても誘発は1回**。効果文に数があればその数だけ
  （「1体を手札に戻す」なら1体だけ）、「1体につき」なら体数ぶん（公式Q&A Q22359・2026-09-18 ユーザー確認）。
  実装は同時破壊グループ（`GameState.destroyGroup`）で、発生源×効果ごとに**解決した時点で**消費する
  （1体しか出ないなら聞かない）
- **順番が結果を変える実例：【不死】（BS09）**（2026-08-14 ユーザー確認）。
  【不死】は「トラッシュにあるこのカードは、自分のコストNのスピリットが破壊されたとき召喚できる」で、
  同じ破壊に対して「フィールドに残る」と**同時に発揮する**。したがって:
  - **「フィールドに残る」を先に解決すると、その個体は破壊されなかったことになり【不死】は発動できない**
  - **【不死】を先に解決できれば発動できる**

  つまりターンプレイヤーの順番の決定が、そのまま【不死】が撃てるかを決める。
  **順番を聞く候補は「復活の確認」だけでなく、その破壊で同時に発揮する効果すべて**である
  （実装は `wouldAskReviveConfirm` の下見を、同時発揮する効果すべてを数える形へ広げること）

## 3. 「フィールドに残る」と「破壊したとき」の関係（接続詞で変わる）

[RESUME_STACK.md §7](./RESUME_STACK.md) に既出。要約:

- **① 別効果の「破壊したとき〜する」**: 復活で**阻止できる**（復活した個体は破壊されていない）
- **② 「破壊することで」「破壊し、そうしたとき」**: 同時発揮なので**阻止できない**

**①②はどちらも「効果による破壊」の話で、＞５のBP比較による勝敗判定とは別**。
BP比較の結果に紐づく『BPを比べ相手のスピリットだけを破壊したとき』も ① と同じで、「残る／戻る」を先に解決すれば阻止できる（§2。2026-11-14 に改めた）。
