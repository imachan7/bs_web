## 0. 結論（先に5行）

1. **合体中のブレイヴは `field.spirits` に置かない。** 実体は `field.combinedBraves` に置き、
   ホストは `braveRefs` で参照する（2026-08-24 確定。§11.2）。
   これで既存のフィールド走査は「合体スピリット＝1体」としか見えず、**走査側は無改修**
2. **BP・シンボルの合成は3関数だけ**（`effectiveBp` / `instanceSymbolCount` / `countSymbols`）
3. **【合体中】効果は `effectSources()` に相乗りすればタダで動く**（専用の効果解決機構は不要）
4. ブレイヴは**レベル表を2つ持つ**（スピリット状態 / 合体状態）。合体状態は Lv1 の必要コアが 0
5. ダイレクトブレイヴは `summon` の**任意パラメータ**で表現する（`level?` を足したときと同じパターン）

## 1. ルール（出典から確定した事実）

### 1.1 基本

- ブレイヴは**カードタイプ**。単体でフィールドに出すと**スピリットとして扱われる**
- 合体すると「ブレイヴスピリット」という **1体のスピリット**になる
- 合体時、合体元に **「コスト」「合体時BP+」「【合体中】効果」「シンボル」「属性」が追加される**
- **スピリット状態のブレイヴ上のコアは、合体スピリット上に置かれる**（＝コアはホスト側に集約）

### 1.2 合体条件

- 「合体条件」を満たすスピリットにのみ合体できる（**系統・コスト・カード名**のいずれか）
- **1体のスピリットに合体できるのは1つまで**
- スピリット状態のブレイヴに他のブレイヴは合体できない
- 合体条件が読点区切りなら、いずれかを満たせばよい
- 例外: 異魔神ブレイヴはスピリット2体までと合体できる（**v1では非対応でよい**）
- 合体条件を満たさなくなったら即座に分離し、スピリット状態にできなければトラッシュ

### 1.3 疲労

- **スピリットかブレイヴのどちらかが疲労状態なら、合体スピリットは必ず疲労状態**になる

### 1.4 場を離れるとき（★ここが挙動の要）

> 自分のフィールド/リザーブから **Lv1の維持コスト以上の数のコアを置くことで**
> 「スピリット状態のブレイヴ」としてフィールドに残すことができる。
> **残さない場合、合体元スピリットと同時にトラッシュに置かれる**

- 「好きにコアを置ける」のではなく、**Lv1維持コスト以上を置けなければ残せない**
- **アタック中の合体スピリットが場を離れても、ブレイヴを残せばアタックは継続される**

### 1.5 シンボル

- **シンボルを持たないブレイヴが実在する**（BS10-062 は「シンボル：なし」）
- シンボルなしのブレイヴを合体しても、合体スピリットのシンボルは元のスピリットのまま

### 1.6 レベル（実カードで確認）

`BS10-062 砲凰竜フェニック・キャノン`:

```
Lv1 スピリット状態: コア3個、BP3000
Lv1 合体状態:      コア0個、BP+3000
```

**ブレイヴはレベル表を2つ持つ。** 合体状態の Lv1 は必要コアが **0個**なので、
コアを1個も持たなくても Lv1 が成立する。

> これは実装上ありがたい。`currentLevel()` は「コア数 ≥ 必要コア数」で判定するため、
> 合体状態のレベル表を渡せばコア0でも Lv1 になる。
> **`Lv0` になって `effectActiveAtLevel` が false を返し、【合体中】効果が無言で発火しない**
> という事故（`TURN_EFFECT_SOURCES.md` §3.3 と同型）は起きない。

## 2. データモデル

### 2.1 `CardType` の拡張

```ts
export type CardType = "spirit" | "nexus" | "magic" | "brave"
```

**影響**: `type === "spirit" | "nexus" | "magic"` の分岐が **33箇所**。
大半は `type === "magic"` の判定でブレイヴには当たらないが、
「スピリットとして扱う」箇所（デッキ検証・召喚可否・UI 表示）は見直しが要る。

### 2.2 `CardData` の追加

```ts
braveLevels?: LevelDef[]   // 合体状態のレベル表。bp は「合体時BP+」の加算値、
                           // cores は合体スピリット上のコア数で判定する
braveCondition?: BraveCondition  // 合体条件
```

```ts
// 合体条件。読点区切りの複数条件は配列＝OR
export type BraveCondition = BraveConditionTerm | BraveConditionTerm[]
export interface BraveConditionTerm {
    family?: string          // 系統
    minCost?: number         // コスト◯以上
    cardName?: string        // カード名指定
}
```

> `TargetFilter`（第1段階で新設）と軸が似ているが、**対象は合体先スピリット1体**であり
> 意味が違うので**共用しない**。将来 `TargetFilter` に寄せたくなったら再検討する。

### 2.3 合体中のブレイヴの置き場（**参照方式**。2026-08-24 確定）

```ts
// PlayerState.field に追加
combinedBraves: CardInstance[]  // 合体中のブレイヴの実体置き場。**フィールド走査の対象に入れない**

// CardInstance（ホスト側）に追加
braveRefs?: { slot: "left" | "right" | "single"; instanceId: string }[]
```

通常のブレイヴは `slot:"single"` の参照1本。異魔神ブレイヴ（1枚がスピリット2体に合体）は
**実体1つ・参照2本**になる。入れ子（`host.braves`）にすると異魔神で実体が2つに増え、
コア・疲労・破壊が同期しなくなる（§11.2）。

**実装で必ず用意するヘルパー**（参照の解決を各所に散らさないため）:

```ts
bravesOf(player, host): CardInstance[]        // ホストに合体しているブレイヴの実体
hostsOf(player, brave): CardInstance[]        // ブレイヴが合体しているホスト（異魔神は2体）
braveLevelOf(host, brave): number             // 合体状態のレベル（braveLevels をホストのコア数で引く）
```

### 2.4 ⚠️ なぜ `field.spirits` に置かないのか（最重要）

ルール上、合体スピリットは **1体のスピリットとして扱われる**。
もし合体中のブレイヴを `field.spirits` に残すと、フィールドを舐める全処理が **2体として数える**。

- `destroyAll` / `exhaustAll` が2体に当たる
- オーラの対象・カウンタが二重に数える
- `countSymbols` がシンボルを二重計上する（＝軽減が過剰になる）

**混色軽減バグ（`be97938`）とまったく同じ「集計が意味を潰す」事故になる。**
別置き場（`field.combinedBraves`）にすれば `field.spirits` には常に1体しか見えず、
**既存の走査は一切変更不要**。

ダイレクトブレイヴの存在もこの設計を裏付ける。合体中のブレイヴは**コアを1個も持たない**ため、
`field.spirits` に置くと**コア0のスピリットとして維持コア割れで即消滅**してしまう。

> **2026-08-24 追記**：この「消滅」は現在 `sweepLevelCostDepletion`（BS09蛇凰神バァラルの
> Lvコスト+1で維持コア割れを掃除する処理）でも走る。合体中のブレイヴを走査対象に入れないことは、
> **バァラルのような後発の効果に対しても効き続ける**前提になっている。

## 3. 合成が必要な関数（**2026-08-25 見直し：3→4→5関数**）

| 関数 | 場所 | 変更内容 |
| :-- | :-- | :-- |
| `effectiveBp` | `shared/rules.ts` | 合体しているブレイヴの「合体時BP+」を加算 |
| `instanceSymbolCount` | `shared/rules.ts` | ブレイヴのシンボル数を加算（ライフダメージに効く） |
| `countSymbols` | `shared/rules.ts` | ブレイヴのシンボル色を加算（軽減に効く） |
| **`instCostDelta`** | `shared/rules.ts` | **ブレイヴのコストを加算**（§1.1「合体時、合体元にコストが追加される」） |
| **`instColors`** | `shared/rules.ts` | **ブレイヴの色を加算＝混色にする**（§1.1「属性が追加される」。2026-08-25 追加。§12.2）。軽減・対象の色絞り込み・装甲判定のすべてに一度で効く |

**この4つで済むのは、リファクタリングで共有ルール層に一本化した直接の成果**。
クライアントも同じ実装を使うため、**BP表示・ライフダメージ・コスト表示が自動的に一致する**
（以前ならクライアントミラーにも同じ改修が必要で、追随漏れが起きていた）。

### 3.1 コストの合成は `instCostDelta` に項を足す（2026-08-24 追加）

設計当時この欄は無かったが、その後 **「コストを読む処理はすべて `instBaseCost` を通る」**形に
一本化された（BS08グロウアップの `instCostDelta`）。合体によるコスト加算もここに項を足せば、
「コスト◯以下を破壊」「同じコストの相手を疲労」などコストを見る判定すべてに一度で効く。
**個別の判定を書き足さないこと。**

### 3.2 シンボル合成で踏みやすい罠（2026-08-24 追加）

`instanceSymbolCount` / `countSymbols` は設計当時より条件が増えている。ブレイヴのシンボルを
足すときは、**既存の分岐と衝突しないか**を確認すること。

| 既存の仕組み | 注意点 |
| :-- | :-- |
| `symbolsOverrideContinuous`（BS08海底に眠りし古代都市のシンボル固定） | 固定された個体はカード静的なシンボルを見ない。**ブレイヴのシンボルは固定の対象か、それとも別枠で足すのか**を決める必要がある |
| `colorsAsContinuous` / `tempColors`（「◯色としても扱う」） | 色ごとに二重に数える経路がある。ブレイヴのシンボルにも適用するか決める |
| `pendingBounce`（バウンス待機中はシンボルを数えない） | ホストがバウンス待機なら、合体中のブレイヴのシンボルも数えないはず |

**§11.1 の「異魔神は2体それぞれにシンボルを加える」は、参照方式なら自然にそうなる**
（各ホストが自分の参照を足すため）。ここは混色軽減バグと同じ「色ごとの突き合わせ」の場所なので、
**合計数ではなく色の内訳で**テストすること。

## 4. 【合体中】効果は `effectSources()` に相乗りする

`effectSources` は**実装済み**（`shared/rules.ts`。2026-08-24 時点で確認）。

```ts
export function effectSources(board: Board, pid: PlayerId): CardInstance[]
```

ここに**合体中のブレイヴを含める**だけでよい。これで `aura` / `constraint` / `keywordGrant` /
`fieldEvent` / `reviveOnDestroy` / `mustBlockGrant` など走査すべてが
【合体中】効果に対応する。ブレイヴ専用の効果解決機構は書かない。

**ただしレベル判定に注意**: 走査側は `currentLevel(source).level` を使う。
合体中のブレイヴは**合体状態のレベル表（`braveLevels`）をホストのコア数で引く**必要がある。
`currentLevel()` に「合体中か」を伝えるか、専用の `braveLevelOf(host, brave)` を用意すること。
**ここを素の `currentLevel()` のままにすると Lv0 になり、【合体中】効果が無言で発火しない。**

### 4.1 現在の `effectSources` に足す前の確認（2026-08-24 追加）

設計当時より入口が増えている。ブレイヴを足すときは、既存の除外条件と噛み合うかを見ること。

- `instEffectsSuppressed`（「持つ効果すべては発揮されない」）を受けたホストの
  **合体中ブレイヴの効果も止まるのか**を決める必要がある（ルールの解釈。実装前に確認する）
- 相手が「相手のネクサスすべての効果は発揮されない」を出している間、ネクサスは丸ごと外れる。
  ブレイヴにも同型の効果が出たときの受け皿を想定しておく
- `turnVirtualInstances`（マジックがこのターンだけ貸した仮想発生源）と並ぶので、
  **`lentOnly` の判定に巻き込まれない**こと（合体中ブレイヴは実在の発生源）

### 4.2 発火の実測が必須（2026-08-24 追加）

`npm run coverage:effects` は**継続効果が一度でも発火したか**を実測する。
2026-08-24 に全 kind へ計測点を入れ、いまは**未計測0件・実行率100%**を維持している。

**ブレイヴで新しい `kind` を足したら、`scripts/coverage-effects.ts` に計測点も足すこと。**
足さないと「未計測の kind」に落ち、**書いたのに一度も発火していない効果が見えなくなる**
（2026-08-24 に45種72件がこの状態で、実際に12件が未発火だった）。

## 5. 召喚（ダイレクトブレイヴ）

### 5.1 アクション

```ts
| { type: "summon"; handIndex: number; level?: number; paySources?: PaySource[]
    substituteInstanceId?: string; discardHandIndices?: number[]
    braveTargetInstanceId?: string }  // 指定時はダイレクトブレイヴ
```

> **2026-08-24 追記**：`summon` には設計当時より任意パラメータが増えている
> （`substituteInstanceId`＝入れ替え召喚、`discardHandIndices`＝手札破棄での支払い）。
> **「任意パラメータを1本足す」というやり方自体は前例が3つに増えて確立している**ので、
> `braveTargetInstanceId` もこの形でよい。

**`pendingChoice` にはしない。** 分岐は完全にクライアント側の操作なので、
「スピリットとして出す / 合体先を選ぶ」を UI で選ばせて **1リクエストで送る**。
`level?` を追加したときと同じパターンで、既存の呼び出しを壊さない。

### 5.2 `doSummon` の分岐

現行はこう。

```ts
const maintain = level === undefined ? lv1Cores(card) : (coresForLevel(card, level) ?? lv1Cores(card))
payCost(state, pid, cost, paySources)
player.reserve -= maintain
const inst = createInstance(cardId, state.turn, maintain)
player.field.spirits.push(inst)
```

ダイレクトブレイヴでは置き場と維持コアだけが変わる（参照方式）。

```ts
// maintain = 0（維持コアを置かない ＝ ダイレクトブレイヴの利点そのもの）
const inst = createInstance(cardId, state.turn, 0)
player.field.combinedBraves.push(inst)                                  // 実体は別置き場へ
host.braveRefs = [...(host.braveRefs ?? []), { slot: "single", instanceId: inst.instanceId }]
// 合体時の疲労合成（1.3）: host.isRested = host.isRested || inst.isRested
```

**神速でも同じ分岐が使える**（フラッシュタイミングの召喚に条件を足さない）。

### 5.3 `RuleValidator` の追加検証

- 対象が**自分のフィールドのスピリット**として実在するか
- カードが `type === "brave"` か
- **合体条件を満たすか**（`braveCondition`）
- **対象に既にブレイヴが付いていないか**（1体1つまで）
- ダイレクトブレイヴでは**維持コアを要求しない**（コストのみ）

## 6. 分離（場を離れるとき）

### 6.1 割り込み位置（2026-08-24 見直し）

`destroySpirit` には既に**破壊への割り込み**がある。**設計当時から場所と形が変わっている**ので、
着手時は現物を読むこと（`server/src/logic/removal.ts`。2026-08-10 に `EffectModules.ts` から移設）。

```ts
tryReviveOnDestroy(state, ownerPid, inst, context, undefined, options?.allowSuspend === true)
```

ブレイヴの分離も**同じ位置に同じ形で挿す**。ただし現在の `destroySpirit` は
`skipRevive` / `allowSuspend` / `deferCommit` の3つの options を持ち、
「その場で聞く」か「恩恵の後で聞く」かを呼び出し元が決める設計になっている
（[RESUME_STACK.md](./RESUME_STACK.md) §7）。**分離の確認もこの使い分けに乗せる。**

### 6.1.1 ⚠️ 場を離れる経路は破壊だけではない

分離は「場を離れるとき」に起きるので、**破壊以外の出口にも同じ処理が要る**。
現在の出口は次のとおりで、**入口ごとに書くと必ず片方を忘れる**。

| 出口 | 関数（`server/src/logic/removal.ts`） |
| :-- | :-- |
| 破壊 | `destroySpirit(cause:"destroy")` |
| 維持コア割れの消滅 | `destroySpirit(cause:"deplete")` |
| 手札に戻る | `returnSpiritToHand` |
| デッキに戻る | `returnSpiritToDeckTop` / `returnSpiritToDeckBottom` |

**共通の入口を1つ用意し、4経路すべてから呼ぶこと**（例: `detachBravesOnLeave(state, pid, host, reason)`）。
コア下限の一件（2026-08-24）と同じで、**共通処理を通さない経路が1つでもあると、そこだけ規則が効かない**。

### 6.2 処理

1. ホストが破壊される（または場を離れる）
2. ブレイヴを残すか判定する。**残すには Lv1維持コスト以上のコアを、自分のフィールド/リザーブから置く**
3. 残す場合: ブレイヴを `field.spirits` へ移し、コアを置く
4. 残せない/残さない場合: ホストと**同時にトラッシュ**へ
5. **アタック中だった場合は `BattleState.attackerInstanceId` をブレイヴへ差し替えてアタックを継続する**
   （`swapBattler`＝テレポートチェンジに同型の処理があるので流用できる）

### 6.3 コアの置き方は**プレイヤーに選ばせる**（2026-08-24 確定。簡略化しない）

設計当時は「`pendingChoice` は候補から1つ選ぶ形しか扱えないので、リザーブから自動で払う簡略化」を
推奨していた。**その前提はもう古い。** 支払い元を選ぶ仕組みは既に動いている。

| 使えるもの | どこで動いているか |
| :-- | :-- |
| 支払いモード（フィールドのスピリット/ネクサス上のコアを1個ずつ割り当てる） | 通常の召喚・配置。クライアントの `PayingState` |
| **選択待ちの解決として支払う**（`resolveChoice` に `paySources` を載せる） | 「コストを支払って召喚できる」起動効果（2026-08-23）、トラッシュからの召喚・マジック使用（2026-08-24） |

分離もこの形に乗る。手順は次のとおり。

1. ホストが場を離れる時点で、持ち主へ確認を出す（`pendingChoice`）
   - 「ブレイヴを残す／残さない」の二択。**残せるコアが無ければ確認を出さずトラッシュへ**
2. 「残す」を選んだクライアントは支払いモードへ入り、`resolveChoice` に `paySources` を載せて送る
3. サーバーは `payCost` 相当でコアを集め、ブレイヴを `field.spirits` へ移してコアを置く

**足りない部品は1つだけ**：現在の支払いモードは「手札／トラッシュのカード1枚」を起点に
コストを計算する（`PayingState.handIndex` + `choiceZone`）。分離では起点が
**場のブレイヴ**で、必要数は**そのブレイヴのLv1維持コスト**になる。
`PayingState` に3つ目の起点を足す必要がある（UI担当へ形を合意してから着手すること。
[INTERRUPTION_POINTS.md](./INTERRUPTION_POINTS.md) §5 の手順4）。

**非対話（テスト・AI）では従来どおり自動で進める**こと（リザーブから払えるなら残す）。
ここを忘れると既存 smoke が大量に落ちる（INTERRUPTION_POINTS.md §5 の手順3）。

## 11. 異魔神ブレイヴ（追記: 2026-07-26）

- 出典: [バトスピ Wiki「異魔神」](https://batspi.com/index.php?%E7%95%B0%E9%AD%94%E7%A5%9E)
- 実カード例: 炎魔神（BSC25-X04）

```
ブレイヴ
5(赤2白2)/赤/異魔神・機竜
<0>Lv1 5000 <0>合体+5000
このブレイヴは、疲労せず、スピリット状態のとき、アタックとブロックができない。
右合体条件：コスト4以上
【右合体中】『このスピリットのアタック時』
  このスピリットのBP以下の相手のスピリット/アルティメット1体を破壊する。
左合体条件：コスト4以上
【左合体中】『このスピリットのアタック時』
  相手のバースト1つを破棄することで、このターンの間、自分のスピリットすべてをBP+5000する。
シンボル：赤
```

### 11.0 結論（先に4行）

1. **「ホストに入れ子」では表現できない**（この節が §2.3 を参照方式に決めた理由）。1つのブレイヴが**2体のホストに同時に属する**ため、
   入れ子にすると実体が2つに増える（コア・疲労・破壊の同期が壊れる）
2. **実体プール＋参照**に変える必要がある。`field.combinedBraves` に実体を1つ置き、
   ホストは `braveRefs: { slot, instanceId }[]` で**参照する**
3. **共通テキストはルールであって効果ではない**（出典に明記）。
   `cards.json` の `constraint` に書いてはいけない。系統「異魔神」でエンジンが解決する（`KEYWORDS` と同型）
4. **シンボルは2体それぞれに加算される**（＝軽減では実質2倍）。参照方式なら §3 の3関数のまま自然にそうなる

### 11.1 ルール（出典から確定した事実）

- 系統「異魔神」を持つブレイヴ。十二神皇編 第2章から表記が「異魔神ブレイヴ」に統一された
- **2体のスピリットと合体できる**。ただし **2体と同時には合体できず、1体ずつ行う**
- **左右で別の合体条件・別の【合体中】効果**を持つ（`右合体条件` / `左合体条件`）
- 共通テキスト:
  > このブレイヴは、疲労せず、スピリット状態のとき、アタックとブロックができない。
  - これは**効果の記述ではないものとして扱い、カードの効果でテキストを打ち消せない**（式鬼魔神の裁定）
- **Lv1コストが0**。スピリット状態でも維持コアを持たないため、
  ネクサス同様**メインステップに任意で消滅させられない**。
  ただしスピリット1体と合体している状態でその合体スピリットを消滅させると、合体元と同じ場所に置かれる
- **シンボル**: 2体と合体している場合、**それぞれのスピリットにシンボルを加える**。
  軽減シンボルを数える場合も、ブレイヴのシンボルを直接数えるのではなく
  **各スピリットにブレイヴのシンボルが加わっているものとして扱う**
- **効果耐性は合体スピリットごとに独立**:
  【装甲：赤】を持つスピリットと持たないスピリットに合体しているとき、
  **装甲を持たない側を対象に赤のマジックを使うと、異魔神ブレイヴは効果を受けて破壊される**
- 複数のブレイヴと合体できるカードでも、**異魔神ブレイヴと合体している場合は他のブレイヴと合体できない**
- 自身と同色の軽減シンボルに加えて**他色の軽減シンボルを持つものが多い**
  （炎魔神は 赤2＋白2。`reduction: Color[]` なので**現行の型でそのまま表現できる**）

### 11.2 ⚠️ データモデル: 入れ子では表現できない（§2.3 を参照方式にした理由）

| 方式 | 異魔神で何が起きるか |
| :-- | :-- |
| **入れ子**（`host.braves: CardInstance[]`） | 2体のホストに**同じブレイヴの実体が2つ**できる。コア・疲労・破壊が同期せず、片方だけ破壊される／シンボルの計上が実体基準で狂う。**混色軽減バグと同型の「意味を潰す」事故** |
| **実体プール＋参照** | 実体は1つ、参照が2本。破壊は実体1つを消して参照2本を切るだけ。**シンボルは各ホストが独立に参照を足すので、出典どおり「それぞれに加算」になる** |

```ts
// PlayerState.field
combinedBraves: CardInstance[]   // 合体中のブレイヴの実体置き場。**走査対象に入れない**

// CardInstance（ホスト側）
braveRefs: { slot: "left" | "right" | "single"; instanceId: string }[]
```

**入れ子と同じ利点は保たれる**——`field.spirits` には合体スピリットが1体しか見えないため、
既存の走査は無改修（§2.4 の主張はそのまま成立する）。追加コストは参照の解決だけ。

### 11.3 判断: v1 から参照方式にする（**2026-08-24 確定**）

| 選択 | 損得 |
| :-- | :-- |
| **v1 から参照方式**（採用） | 通常ブレイヴでは `slot: "single"` の参照1本。実装量の差はわずかで、異魔神・将来の複数合体がそのまま乗る |
| ~~v1 は入れ子、異魔神で移行~~ | §3 の関数・§4 の `effectSources`・§6 の分離処理を**もう一度書き換える**。移行時に「実体が2つ」の罠を踏む危険が残る |

参照方式にしても §5（ダイレクトブレイヴ＝`summon` の任意パラメータ）と
§6（分離の割り込み位置）の設計は変わらない。**変わるのは置き場だけ。**

### 11.4 共通テキストは `cards.json` に書かない

出典が「**効果の記述ではないものとして扱い、カードの効果で打ち消せない**」と明記している。
`constraint` として `cards.json` に載せると:

- 「テキストを打ち消す」「効果を受けない」系の経路（`immuneToOpponentThisTurn` など）で
  **消える対象になってしまう**
- レベル指定（`levels`）が絡み、Lv1コア0＝Lv判定の縁で無言に消える危険がある（§1.6 と同型）

したがって **`family` に「異魔神」を持つブレイヴはエンジン側でハードコードする**。
`KEYWORDS` レジストリ（カードデータは名前だけ持ち、挙動はエンジンが解決する）と同じ方式:

```ts
// 系統「異魔神」を持つブレイヴのルール（打ち消し不可）
export function isImajin(card: CardData): boolean { return card.family.includes("異魔神") }
// - 疲労しない: 疲労合成（§1.3）の対象外。exhaust 系の全経路でガード
// - スピリット状態のとき: cantAttack / cantBlock 相当（合体中は制限なし）
```

**§1.3 の疲労合成ルールの例外**になる点に注意。
「スピリットかブレイヴのどちらかが疲労なら合体スピリットは疲労」に対し、
**異魔神は疲労しないので合成に寄与しない**。

### 11.5 左右スロットの効果

```ts
// EffectDef に足す（合体中効果のスロット限定）
braveSlot?: "left" | "right"   // 省略＝どちらでも（通常ブレイヴの【合体中】）
```

`effectSources()`（§4）が合体中ブレイヴを含めるとき、**どのホストのどのスロットとして
出しているかを渡す**必要がある。参照方式なら「ホスト → 参照」の向きで走査するので自然に決まる
（実体から逆引きすると2ホストのどちらか判別できない＝ここも参照方式が有利な点）。

**効果は左右の順に発揮させることでコンボになるものが多い**（出典）。
発揮順は「左→右」で固定する（`braveRefs` の順ではなく `slot` で決める）。

### 11.6 分離・破壊

- 異魔神ブレイヴが**効果を受けて破壊される**とき（§11.1 の装甲の例）:
  実体を1つ破壊し、**両ホストの `braveRefs` から参照を切る**
- ホスト側が場を離れるとき: §6 と同じ割り込み位置。ただし**もう一方のホストにまだ合体している**場合は、
  スピリット状態に戻さず**参照を1本切るだけ**（合体状態を維持する）
- **Lv1維持コアが0**なので、§6.2 の「Lv1維持コスト以上のコアを置けば残せる」は
  **常に成立する**（0個で残せる）。異魔神は分離で失われない
- 【マイユニット】で合体スピリットを並べ替える裁定があるが、**該当機構が未実装なので範囲外**

## 12. 確定した一般則（2026-08-25 ユーザー確認。**7件すべて回答済み**）

CLAUDE.md の「ゲームルールの解釈は、実装前に設計を示して確認する」に沿って聞いた7件と、
その場で追加で示された2件。**どれも複数のカードに一般則として効く**ので、1枚ずつ判断しないこと。

| # | 論点 | 確定した答え |
| --: | :-- | :-- |
| 1 | ホストが「持つ効果すべては発揮されない」を受けたとき、**合体中ブレイヴの【合体中】効果も止まるか** | **止まる**。合体スピリットは1体なので、その1体の効果が止まる |
| 2 | ブレイヴ自身が効果の**対象**になれるか（「スピリット1体を破壊」でブレイヴだけ狙えるか） | **狙えない**。合体中は1体のスピリットで、対象はホスト側 |
| 3 | 合体スピリットが**シンボル固定**（BS08海底に眠りし古代都市）を受けたとき、ブレイヴのシンボルはどうなるか | **固定が勝つ**。赤シンボルのブレイヴを合体していても、青2つに固定されれば青になる |
| 4 | 合体スピリットの**維持コア**は、ホストのLv1コストだけで判定してよいか | **ホストのLv1コストだけ**。ブレイヴは合体中Lv1が0コアなので寄与しない |
| 5 | **バァラル型のLvコスト+N**（BS09-017）は合体スピリットにどう効くか | **ホストのLvコストだけ**が上がる。ブレイヴの合体状態レベル表は影響を受けない |
| 6 | 分離して残ったブレイヴは、その**ターンに召喚されたもの**として扱うか | **扱わない**。場に出続けていたものが状態を変えただけ |
| 7 | アタック中に分離してブレイヴがアタックを継続するとき、**アタック時効果は再発揮するか** | **しない**。アタック宣言は1回きり |

### 12.1 ⚠️ 発生源の**種別**：ブレイヴを "spirit" に丸めない（2026-08-25 追加確認）

**【装甲：色】の効果文は「指定された色の相手の“スピリット/ネクサス/マジック”の効果を受けない」で、
ブレイヴを列挙していない。** したがって:

| 効果 | 発生源の種別 | 【装甲】で防げるか |
| :-- | :-- | :-- |
| **ブレイヴ自身**の効果（単体で場に出たブレイヴの『召喚時』など） | `"brave"` | **防げない**（防げるのは【重装甲】だけ） |
| **合体中**にブレイヴがホストへ付与している効果（『このスピリットのアタック時』など） | `"spirit"`（合体スピリット） | **防げる** |

- 【重装甲】は**ブレイヴ登場以降のキーワード**で、いまのプールに0枚。カードが入ったら実装する
- 実装上は `sourceType` / `srcType` に **`CardType` をそのまま流す**（"brave" を "spirit" に変換しない）。
  除外は耐性の唯一の判定表 `boardResistanceAgainst`（`shared/rules.ts`）で1回だけ行う。
  ⚠️ 2026-08-25 の段階1で一度「brave→spirit に丸める」実装を入れて**撤回した**。丸めると装甲が過剰に効く

### 12.2 ⚠️ 発生源の**色**：合体スピリットは混色。ただしシンボルは合成するだけ（2026-08-25 追加確認）

- 合体スピリットの色は **ホストの色＋ブレイヴの色**＝**混色扱い**になる。
  軽減・「相手の〈色〉のスピリット」の絞り込み・装甲の判定は、すべてこの合成後の色で行う
- **色が混ざってもシンボルはそのまま**。合体スピリットのシンボルは
  「ホストのシンボル＋ブレイヴのシンボル」を素直に並べたもので、
  **色が混色になったからといってシンボルの色まで混ざるわけではない**（多色カードと同じ扱い）
- 一方、分離中（スピリット状態）のブレイヴ自身の効果は、発生源がそのブレイヴ単体なので**ブレイヴの色だけ**

> これにより §3 の「合成が必要な関数」に **`instColors`（色の合成）が加わって5関数**になる。
