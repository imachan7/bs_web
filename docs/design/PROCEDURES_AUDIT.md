# 手順の棚卸し（「誰も決めていないのに決まっている」箇所の一覧）

2026-08-17 作成。**ゲームの手順が、どこまで文書化されていて、どこからは実装が勝手に決めているか**を
機械的に洗い出した記録。

> カード906枚の「効果の語彙」は SPEC.md に厚く書かれているが、**ゲームの「手順」はほとんど書かれていない**。
> そのため手順は `doSummon` の文の並び順のような形で暗黙に存在し、誰も決めていないのに決まっている状態になる。
> — CLAUDE.md

この文書はその「暗黙に決まっているもの」を可視化するためのもので、**正解を決める文書ではない**。
決まったことは各手順書（下の §2 の索引）へ移し、ここからは消す。

## 0. 結論（先に5行）

1. **文書にあるのに実装が従っていない規則が1つある**：同時発揮の解決順（→ §3）
2. **対戦者が選ぶべき場面を実装が自動で決めている箇所が57件**ある（→ §4）
3. 手順書は9本あるが**索引がなかった**ので §2 に作った（同じ規則を何度も発見し直すのを防ぐ）
4. **既存の `audit:semantics` はこの層を見ていない**。データと効果文しか突き合わせないので、
   「ハンドラ実装が対象を勝手に選んでいる」は検出できない（→ §6 の S9 提案）
5. 同時発火（2件以上が同じタイミングで発揮）は smoke 全体で**38回だけ**＝稀。
   「順番を聞く」実装にしても対戦の煩雑さは小さい

### この索引に**無い**もの（＝どこにも書かれていない決定）

- **誘発の走査順**：`fireStepTriggers` は「ターンプレイヤー側 → 相手側」、各プレイヤーの中は
  **`[スピリット…, ネクサス…]` の並び順（＝場に出た順）**。`fireFieldEventTriggers` と
  `fireBattleWonTriggers` は**片側しか走査しない**（呼び出し側が `pid` を決める）
- **ターン開始処理の区間の切り方**：`start → core → draw① → draw② → refresh → main` の6区間。
  ドローステップを①②に分けているのは「ドローより前に発火する効果」を成立させるため（`PhaseManager.ts` のコメント）
- **レベル変動の反映タイミング**：`currentLevel` が都度計算する＝コアが動いた瞬間に即時反映
- **コア移動の粒度**：1個ずつか一括か（アクションごとにばらばら）
- **対象を決める時点**：効果の解決時に決めるのか、宣言時に決めるのか

## 3. ⚠️ 文書にあるのに実装が従っていないもの

### 同時発揮の解決順（TIMING_CHART §0-3）

> A と B のそれぞれの中で複数が同時に発揮する場合は、**ターンプレイヤーが解決順を決める**

**この規則を守っているのは破壊処理だけ**（`PendingChoice.destroyOrder`。「フィールドに残る」と
【不死】が2体以上に出るならターンプレイヤーに順番を聞く）。

**誘発（`step` / `fieldEvent` / `battleWon` / `triggered`）は聞いていない。**
`resolveInOrder` が受け取った配列の順、つまり**場に出た順**で解決する。

| | 実装 | TIMING_CHART §0-3 |
| :-- | :-- | :-- |
| 破壊の解決順 | ターンプレイヤーに聞く | 一致 |
| 誘発の解決順 | 場に出た順で固定 | **未追随** |

**実測**：smoke 全体で同時発火（2件以上）は**38回**（35回が2件、2回が4件、1回が6件）。
稀なので「聞く」実装にしても煩雑になりにくい。

## 4. ⚠️ 対戦者が選ぶべき場面を実装が自動で決めている（57件）

`interactiveTargets` の分岐が無い＝**実対戦でも自動**の箇所。性質ごとに:

| 性質 | 件数 | 例 |
| :-- | :-- | :-- |
| **対象選択を自動で決めている** | 27 | 「実効BP最大の1体」「コスト最大から貪欲に」「フィールドの先頭側」に固定 |
| 任意（「〜できる」「〜することで」）を自動発動 | 7 | 払うかどうかを聞かずに常に払う |
| 順番を自動で決めている | 5 | 「好きな順番でデッキに戻す」を記録順で固定 |
| 枚数・個数を選ばせていない | 3 | 「好きなだけ破棄する」を全部破棄で固定 |
| 条件やタイミングの近似 | 5 | 「このフラッシュタイミングで」をバトル単位で近似 |
| その他 | 10 | |

影響カード枚数の多い順（上位。`ActionHandler<"...">` から機械推定）:

| 枚数 | action type | 場所 |
| :-- | :-- | :-- |
| 38 | `refreshSelf` | `actions/exhaustRefresh.ts:596,617` |
| 12 | `deckReveal` | `actions/handDeck.ts:569` |
| 11 | `destroyNexus` | `actions/destroy.ts:689` ほか（**対象選択がそもそも無い**。2026-08-17 発見） |
| 10 | `lifeCrush` | `actions/battleFlow.ts:200,253` |

## 5. どこにも書かれていない決定（質問リスト）

「私はこう解釈しました → これでいいですか」の形で並べる。**答えが出たら §2 の索引先へ1行として移す。**

| # | 論点 | 実装の現状 | 解釈案 |
| :-- | :-- | :-- | :-- |
| Q1 | 誘発が複数同時に発揮するときの解決順 | 場に出た順で固定 | TIMING_CHART §0-3 に従い、**2件以上なら毎回ターンプレイヤーに聞く**（破壊と同じ形）。同時発火は稀（38回）なので煩雑にならない |
| Q2 | 対象選択の自動化（27件） | 「実効BP最大」等に固定 | **影響枚数の多い順に選択式へ直す**。段階的に、1バッチずつ |
| Q3 | 任意コストの自動発動（7件） | 常に払う | 「〜できる」は確認式（2026-08-15 に14枚で確定した方針の適用漏れ） |
