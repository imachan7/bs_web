## 0. 結論（先に6行）

1. **`field.ultimates` を新設し、`field.spirits` には入れない。** ルールの既定が
   「スピリットを対象にする効果はアルティメットに当たらない」なので、**書き漏らしが安全側に倒れる**
2. **`lv1Cores` → `minLevelCores` の一般化が最初の関門**（呼び出し **24箇所**）。
   アルティメットは **Lv3始まり**（アポロドラゴンは Lv3＝コア1個）。ここを直さないと
   **召喚直後に Lv0 になって消滅する**
3. 究極シンボル「極」は**色ではない**。`Color` に足さず `SymbolMark = Color | "ultimate"` を作る。
   **軽減（色ごと）では数えず、ライフダメージ（シンボル数）では数える** ＝ 混色軽減バグと同じ A/B 分類
4. 召喚条件は「**いかなるタイミングでも**満たさなければ召喚できない」。
   スピリットを場に出す経路は**実測2箇所**しかないので、関門は2つで足りる
5. 【Uトリガー】は**デッキ破棄ではない**。`millDeck` を流用すると
   `fieldEvent "opponentDeckMilled"` が誤発火し、デッキ破棄メタに引っかかる
6. **アルティメットは「スピリットを数える」効果の分母に入らない。**
   `field.spirits.length` を数えている既存箇所は**変更不要**（配列を分ける最大の利点）

## 1. ルール（出典から確定した事実）

### 1.1 基本

- ブレイヴに続く**第5のカードカテゴリ**。2013年秋の「アルティメット編」から
- スピリットの**進化系**であり、**最低 Lv3 から始まる**。Lv3 時点で同コスト同Lvのスピリット相当のBP
  （例: 龍皇ジークフリード Lv3 BP10000 ＝ アルティメット・ジークフリード Lv3 BP10000）
- 色はカードフレームの色で表される（＝スピリットと同じ色体系を持つ）
- 召喚手順はスピリットと同様

### 1.2 究極（アルティメット）シンボル ＝ 「極」

- アルティメット独自のシンボル。**従来の6属性の軽減には使えず、色を持つものとして扱わない**
- ただし「**究極シンボルを軽減シンボルに持つカード**」の軽減には使える（アルティメットバトル02以降）
- 「色とシンボルを無色として扱う」効果が発揮されていても、究極シンボルとして軽減できる

### 1.3 召喚条件

- カードに書かれた「**召喚条件**」を満たすか、「召喚条件を無視する」効果が発揮中でなければ、
  **いかなるタイミングでも召喚できない**
- 《煌臨》でフィールドに出す場合は召喚条件を満たす必要がない（v1の範囲外）
- 実例（アポロドラゴン）: 【召喚条件：自分の赤スピリット1体以上】

### 1.4 フィールドでの扱い（★ここが本機構の核）

- フィールドにおいても**スピリットではなくアルティメットとして扱う**
- 原則、**対象に「アルティメット」と書かれている効果を受ける**。
  従来のスピリットを対象にする効果は**受けない**
- 【激突】やフィールドを対象にする効果も、対象にアルティメットと書かれていなければ掛からない
- **ルールマニュアル Ver.9.0（2018-04-21）以降**、
  「フィールドのコアやカードを対象にする効果」は**受ける**（優遇の一部廃止）
- フィールド以外で単に「カード」を対象とした効果は受ける（トラッシュ回収など）

### 1.5 ブレイヴとの関係

- **合体条件にアルティメットと書かれているブレイヴとだけ合体できる**
- スピリットではないので、合体条件にアルティメットと書かれていないブレイヴとは合体できない
- 合体中のブレイヴは Ver.9.0 以降、従来のブレイヴを対象にする効果を受ける

### 1.6 専用キーワード

【Uトリガー】/【WUトリガー】/【TUトリガー】/【QUトリガー】/【OUトリガー】/【XUトリガー】/
【CUトリガー】/【Uハンド】/【Uエナジー】/【U抜刀】/【ソウルドライブ】。
召喚に関与するものとして【スピリットソウル】。

**神皇編以降はキーワードを持たないアルティメットも多い**ので、
キーワードは「アルティメットの必須要素ではない」前提で設計する。

### 1.7 【Uトリガー】の詳細

```
【Uトリガー】LvX『(発揮タイミング)』
Uトリガーがヒットしたとき、(効果テキスト)。
（Uトリガー：相手デッキの上から1枚をトラッシュに置く。
  そのカードのコストが、このアルティメットより低ければヒットとする）
```

- **相手の**デッキトップを**トラッシュに置く**。コストが**自身のコストより低ければヒット**
- **「デッキ破棄」には当たらない**:
  - デッキ破棄無効で防げない
  - **破棄されたときに発揮する効果も発揮できない**
  - 青の【強化】でトリガーの枚数を増やせない
- 【WUトリガー】＝2枚、【TUトリガー】＝3枚（以下同様の派生）。
  「**ヒットしたUトリガー1回につき**」と「【ダブルヒット】＝2回ヒットで追加効果」がある
- ヒット効果の対象指定・任意効果の選択は、相手の【トリガーカウンター】解決後に行う
- 実例（アポロドラゴン Lv4-5）:
  「ヒットしたUトリガー1回につき、BP9000以下の相手のスピリット1体を破壊する。
  【ダブルヒット】：Uトリガーが2回ヒットしたら、さらに、相手のライフのコア1個を相手のリザーブに置く。」

## 2. ⭐ なぜ `field.spirits` に入れないのか（BRAVE.md との対比）

現行の `field.spirits` 参照は **159箇所**（`server/src` + `shared`。クライアントは8箇所）。
アルティメットをここに混ぜると、その **159箇所すべてが暗黙にアルティメットを含む**。

| 誤りの方向 | 何が起きるか | 気づけるか |
| :-- | :-- | :-- |
| `field.spirits` に混ぜて、除外を書き漏らす | スピリット指定の破壊・疲労がアルティメットに当たる／「自分のスピリット3体以上」の分母に入る | **気づけない**（テストは全緑のまま、ルール違反だけが起きる） |
| 配列を分けて、`battlers()` への置換を書き漏らす | アルティメットがアタック・ブロック・コア維持の対象から漏れる | **すぐ気づく**（アタックできない・消滅しない＝目に見える） |

**ルールの既定が「受けない」なので、分離のほうが安全側に倒れる。**
これは BRAVE.md §2.4 の「入れ子にする」判断と**同じ原則の別解**であり、結論は共通している
——**`field.spirits` に混ぜない**。

### 2.1 走査の分類（`docs/archive/HANDOFF_DESIGN.md` §4.4 の A/B 分類に第3軸を足す）

| その走査が問うていること | 使うもの | 例 |
| :-- | :-- | :-- |
| **バトル・アタック・ブロック・コア維持・レベル**（＝カード実体としての振る舞い） | `battlers(player)`（新設。`[...spirits, ...ultimates]`） | `validateAttack` / `resolveBattle` / 維持コア割れ判定 / `findInstanceAnywhere` |
| **「スピリット」を数える／対象にする** | `field.spirits` のまま（**変更不要**） | `destroyAll` / aura の `ownAll` / `ownColorSpiritsAtLeast` / 召喚数制限 |
| **誰が継続効果を出しているか**（分類A） | `effectSources()` に `ultimates` を足す（**1箇所**） | aura / constraint / keywordGrant / fieldEvent の全走査 |
| **盤面に何が存在するか**（分類B。シンボル集計） | 究極シンボルの扱いに注意（§5） | `countSymbols` / `instanceSymbolCount` |

**この分類表を作ることが移行作業の本体**であり、159箇所を機械的に置換してはいけない。

### 2.2 「アルティメットを対象に取る」効果の表現

`TargetFilter`（第1段階で新設済み）に**軸を1つ足すだけ**でよい。

```ts
export interface TargetFilter {
    // ...既存の軸
    kinds?: ("spirit" | "ultimate")[]  // 省略時は ["spirit"]（＝既存カードの意味を変えない）
}
```

**省略時が `["spirit"]`** なので、既存 44枚・57箇所のデータは**1文字も変えずに正しい意味**になる。
これは TargetFilter 直交化（第1段階）の成果が最も効く場所。
`matchesTarget` が候補集合を `field.spirits` / `field.ultimates` のどちらから引くかを
`kinds` で決める形にする。

## 3. データモデル

```ts
export type CardType = "spirit" | "nexus" | "magic" | "brave" | "ultimate"
```

**影響**: `=== "spirit" | "nexus" | "magic"` の分岐は **44箇所**（クライアント含む・実測）。
ブレイヴ導入と合わせて一度に点検するのが安い。

```ts
// CardData
symbol: SymbolMark[]        // 究極シンボルを含みうる（アポロドラゴンは ["ultimate"]）
reduction: SymbolMark[]     // 「究極シンボルで軽減できるカード」も表現できる
summonCondition?: SummonCondition   // アルティメットは必須（validate-cards で検査する）
levels: LevelDef[]          // Lv3/4/5。**Lv1 を持たない**
```

```ts
export type SymbolMark = Color | "ultimate"
```

```ts
// PlayerState.field
field: {
    spirits: CardInstance[]
    ultimates: CardInstance[]   // 新設
    nexuses: CardInstance[]
}
```

`CardInstance` は**変更なし**（コア・疲労・レベルの構造はスピリットと同じ）。

## 4. ⚠️ Lv3始まりの罠 — `lv1Cores` を一般化する

現行の維持コアは **「Lv1 の必要コア数」をハードコード**している。

```ts
// server/src/logic/GameState.ts
export function lv1Cores(card: CardData): number {
    const lv1 = card.levels.find((l) => l.level === 1)
    return lv1 ? lv1.cores : 0      // ← Lv1 が無いカードは 0 になる
}
```

アルティメットは Lv1 を持たない（アポロドラゴンは `<1>Lv3 <3>Lv4 <5>Lv5`）ため、
**このまま召喚すると維持コア0個で場に出て、`currentLevel` が Lv3 の必要コア1個を満たさず Lv0 になる。**

`currentLevel` 自体は「コア数 ≥ 必要コア数の最大レベル」を選ぶ実装なので、
**Lv3始まりの表をそのまま渡しても正しく動く**。壊れるのは維持コアの側だけ。

### 4.1 提案する変更（挙動保存）

```ts
// 維持コア数 ＝ そのカードが持つ最小レベルの必要コア数
export function minLevelCores(card: CardData): number {
    let min: LevelDef | undefined
    for (const lv of card.levels) if (!min || lv.level < min.level) min = lv
    return min ? min.cores : 0
}
```

**既存カードは全て Lv1 を持つので、値は 1文字も変わらない**
（＝既存 smoke を書き換えずに通ることが挙動保存の根拠になる。`docs/archive/HANDOFF_DESIGN.md` §4.5）。

呼び出しは **24箇所**（`RuleValidator` 3 / `EffectModules` 6 / `actions/cores.ts` 5 /
`GameEngine` 4 / `actions/battleFlow.ts` 2 / `actions/destroy.ts` 1 / import 3）。
`lv1Cores` を**削除して改名**すれば、tsc が漏れを全部指摘する（TargetFilter 第2段階と同じ手）。

### 4.2 この関数は SOULCORE と共有する

ソウルコアの「動かすと自身が消滅する場合は発揮できない」判定も同じ関数を使う
（[SOULCORE.md](./SOULCORE.md) §4.3）。**2機構の唯一の接点**なので、先に入れておくとどちらからも使える。

## 5. 究極シンボルの扱い（A/B 分類がそのまま効く）

| 用途 | 関数 | 究極シンボルは | 理由 |
| :-- | :-- | :-- | :-- |
| コスト軽減 | `countSymbols` | **数えない**（色として） | 「6属性の軽減には使えず、色を持つものとして扱わない」 |
| コスト軽減（究極シンボルを軽減に持つカード） | `countSymbols` | **数える** | 「究極シンボルを軽減シンボルに持つカードの軽減に使える」 |
| ライフダメージ | `instanceSymbolCount` | **数える**（1個＝1点） | シンボル数そのもの。色は無関係 |
| デッキビルダーの色内訳 | `buildPreset` 等 | 色として数えない | 表示上は「極」として別枠 |

これは `docs/archive/MULTICOLOR.md` が確立した「**軽減・ライフダメージ・単色プリセットの3つは OR にしてはいけない**」と
同じ構造の判断。`.symbol` 参照は **13箇所**、`.reduction` は **5箇所**しかないので、
シンボル周りの改修量そのものは小さい。

**注意**: `countSymbols` に「究極シンボルを色として数えない」を入れる際、
**`ownFieldSymbolColors`（分類B）にも同じ判断を入れる**こと。片方だけ直すと
「軽減はされないのに色は数える」というズレが出る。

## 6. 召喚条件

### 6.1 型

```ts
// v1は最初の実装バッチに必要な条件だけを並べる（既存の condition 語彙と同じ命名にそろえる）
export type SummonCondition =
    | { ownColorSpiritsAtLeast: { color: Color; count: number } }   // 自分の赤スピリット1体以上
    | { ownFamilyCountAtLeast: { family: FamilyFilter; count: number } }
    | { ownLifeAtMost: number }
    | { ownTrashCardsAtLeast: number }
```

> **条件語彙の統一はしない。** 現在 `triggered.condition` / `magic.condition` / `AuraCondition` /
> `step.condition` が別々に育っている。ここを一括統一するのは TargetFilter 直交化と同規模の
> 別タスクであり、アルティメット導入と混ぜると**挙動保存の根拠が取れなくなる**。
> まずは `SummonCondition` として独立させ、統一は別途判断する。

### 6.2 関門は2つで足りる（実測）

スピリットを場に出す経路は**2箇所しかない**。

| 経路 | 場所 |
| :-- | :-- |
| 通常召喚・神速召喚・レベル指定召喚 | `GameEngine.ts:213`（`doSummon`） |
| 効果による無償召喚 | `EffectModules.ts:1175`（`summonFromHandFree`） |

`RuleValidator.validateSummon` に `checkSummonCondition` を足し、
**効果召喚の経路（`summonFromHandFree`）にも同じ関門を通す**。
「いかなるタイミングでも召喚できない」＝**効果による召喚も条件を満たさなければ不発**。

> ここは「実装されているが誰も通っていない経路」の逆パターン＝**関門を通っていない経路**。
> 神速召喚が `doSummon` を共有していることは確認済みだが、
> 将来《煌臨》を足すときは**第3の経路**になる（煌臨は条件不要なので、意図的に関門を通さない）。

## 7. 【Uトリガー】

### 7.1 型

```ts
| {
    kind: "uTrigger"
    levels: number[] | null
    count: number              // 1=U / 2=WU / 3=TU …（めくる枚数）
    trigger: TriggerEvent      // 『このアルティメットのアタック時』＝ onAttack
    action: EffectAction       // ヒット1回につき実行する効果
    perHit?: boolean           // true: ヒット数ぶん繰り返す（既定）／false: 1回だけ
    doubleHitAction?: EffectAction   // 【ダブルヒット】＝2回以上ヒットで追加
  }
```

### 7.2 ⚠️ `millDeck` を流用してはいけない

`millDeck` は現在 `fieldEvent "opponentDeckMilled"` を発火し、
【粉砕】と同じ「デッキ破棄」として扱われる。Uトリガーは**デッキ破棄ではない**ので:

- `opponentDeckMilled` を**発火させない**
- デッキ破棄無効・破棄枚数修正（`funsaiBonus` 系）の影響を**受けない**
- 破棄されたカードの「トラッシュに置かれたとき」誘発も**発火しない**

専用の `resolveUTrigger(state, owner, self, count): number`（戻り値＝ヒット数）を書き、
**デッキ操作を直接行う**。デッキが0枚でも敗北しない（敗北はドロー不能時のみ＝現行と同じ）。

### 7.3 ヒット判定

```
ヒット ⇔ めくったカードの cost < このアルティメットの cost
```

`cost` は**カードの素のコスト**か、`effectiveCost`（軽減・costMod 適用後）か。
出典は「そのカードのコスト」としか書いていない。**素のコストで実装するのが自然**
（`effectiveCost` は使用者側の盤面に依存するため、相手デッキのカードには意味を持たない）。
※ ここは「未確定」として §11 に記録する。

## 8. ブレイヴとの合体

`BraveCondition`（BRAVE.md §2.2）に**アルティメットを指す軸**を足す。

```ts
export interface BraveConditionTerm {
    family?: string
    minCost?: number
    cardName?: string
    kind?: "spirit" | "ultimate"   // 追加。指定時はそのカテゴリにのみ合体できる
}
```

- 合体条件に `kind: "ultimate"` が無いブレイヴは**アルティメットに合体できない**
- 合体先がアルティメットのときも、**入れ子の置き場はホスト側**（BRAVE.md §2.3 と同じ）
- 合体中ブレイヴは Ver.9.0 以降「ブレイヴを対象にする効果」を受ける
  （＝`TargetFilter.kinds` に `"brave"` を足すかは、ブレイヴ実装時に判断）

## 9. 段階移行

各段で `npm run typecheck && npm run smoke:quiet && npm run validate:cards` が緑であること。
**既存 smoke を書き換えずに通ることを挙動保存の根拠にする。**

| 段 | 内容 | 検証 |
| --: | :-- | :-- |
| 0 | `lv1Cores` → `minLevelCores`（§4）。**この段だけ単独でコミットできる** | 既存が無変更で通る（値が変わらないこと） |
| 1 | `SymbolMark` の導入（§5）。データは全て色のままなので挙動不変 | 既存が無変更で通る |
| 2 | `CardType` に `"ultimate"`／`field.ultimates`／`battlers()` の新設。**まだ召喚できない** | 既存が無変更で通る |
| 3 | §2.1 の分類表にもとづく 159箇所の仕分け（`battlers()` への置換） | アタック・ブロック・維持コア割れの smoke |
| 4 | 召喚条件（§6）＋召喚経路2つ | 条件未達で召喚不可・効果召喚でも不可 |
| 5 | `TargetFilter.kinds`（§2.2）＝「スピリット指定効果が当たらない」 | **アルティメットが破壊されないこと**の smoke |
| 6 | 【Uトリガー】（§7） | ヒット/ミス/ダブルヒット・`opponentDeckMilled` が発火しないこと |
| 7 | 実カードの構造化（まずアポロドラゴン1枚を通す） | カードごとの smoke |
| 8 | クライアント（極シンボル表示・アルティメット枠）※ Gemini 担当 | 目視 |

## 10. `validate-cards.ts` に追加すべき検査

- `type === "ultimate"` なら `summonCondition` を持つこと（**召喚条件を持たないアルティメットは存在しない**）
- `type === "ultimate"` の `levels` は **Lv1 を含まない**こと（最小レベルが3以上）
- `levels` が**レベル昇順**かつ `cores` も昇順であること（`minLevelCores` の前提）
- `symbol` に `"ultimate"` を含むのはアルティメットのみであること
- `kind: "uTrigger"` の `count` が 1以上であること／`levels` が `null` でないこと
  （`lendSelfThisTurn` の検査と同型の「無言で発火しない」防止）
