# AI対戦相手の設計（2026-08-23）

**AI の強さを変えたい・AIが変な手を打つのを直したいときに読む。**
実装は `server/src/ai/`（4ファイル・約350行）。方針は 2026-08-23 のユーザー判断で
「**ルールベースの1手評価**（先読みなし）」に決めた。

## 1. なぜこの作りか

強さより **止まらないこと** が要件。AIが手を選べずに固まると、対戦者は画面の前で
何も操作できないまま待たされる（相手が人間なら「切断」で片が付くが、AI戦には逃げ道がない）。
そのため次の2つを設計の芯に置いた:

- **合法手は必ず1つ以上残る**。メインなら `nextPhase`、アタックステップなら `endTurn`、
  フラッシュなら `pass`、選択待ちならスキップが常に候補に入る
- **可否の判定を自前で書かない**。`RuleValidator` の `validateXxx` は副作用のない検証関数なので、
  候補を作っては捨てる用途にそのまま使える。「AIが打てるつもりの手をサーバーが弾く」ズレが構造的に起きない
  （クライアントUIが `activatableAbility` を通してボタンを出すのと同じ考え方）

## 2. 3つの層

| ファイル | 役割 | 入力 |
| :-- | :-- | :-- |
| `legalMoves.ts` | 今打てる手をすべて列挙する | `GameState`（`validateXxx` が要求するため） |
| `evaluate.ts` | 1手ずつ点数を付ける | **`GameView`**（AI自身の視点） |
| `runner.ts` | 対戦中に1手ずつ進める・安全弁 | `GameState` |
| `index.ts` | 上2つを繋ぐ `decideAiAction` | — |

### ⚠️ AI に相手の手札を覗かせない仕組み

**評価関数が受け取るのは `GameState` ではなく `GameView`**（`viewFor(state, pid)` の結果）。
GameView は相手の手札・デッキ内容を持たないので、AIが盤面の裏を見て指すことが型の上で起こらない。
これが成立するのは `shared/board.ts` の `_GameViewIsBoard` があるおかげで、
共有ルール層（BP計算・ブロック可否・コスト）を GameView のまま呼べる。

**評価に `GameState` を渡す形へ変えないこと。** 一度渡すと、相手の手札を見た判断が
いつのまにか混ざっても誰も気づけなくなる。

列挙のほうは `GameState` を使うが、`validateXxx` は「その手が合法か」しか答えないので
情報の非対称は生まれない。

## 3. 点数表（`evaluate.ts`）

高いほど打ちたい手。同点なら列挙順（＝決定的に選ぶ）。

| 手 | 点数 | 補正 |
| :-- | :-- | :-- |
| アタック | 100＋BP/1000 | 止める相手がいない +60（相手ライフ1なら +300）／返り討ちにされる相手がいる −50／**守りが残らない −130** |
| 召喚 | 80＋BP/1000＋シンボル×5 | 払える最大レベルで出す |
| 起動能力 | 70 | |
| コアを置く | レベルが上がるなら75／上がらないなら5 | 上がらないコアはリザーブに残す |
| ネクサス配置 | 60 | |
| マジック | バトル中65／それ以外45 | |
| ブロック | 相手より強い150／相打ち60／負ける10（自ライフ2以下なら70）／自ライフ1なら200 | |
| ライフで受ける | 20＋ライフ×15（ライフ1なら0） | ブロックの点数と釣り合わせてある |
| フラッシュをパス | 40 | |
| アタックステップへ | 20 | |
| ターン終了 | 5 | 他に何も無いときだけ |
| 選択待ちへの応答 | 下記 | |

**選択待ち（`resolveChoice`）は候補の持ち主で符号を変える**のが基本則。
同じ `resolveChoice` で「相手のものを選ぶ場面（破壊・疲労）」と
「自分のものを選ぶ場面（コスト・破棄）」の両方が来るため:

- フィールドの個体：相手のものなら強い個体（50＋強さ）、自分のものなら弱い個体（50−強さ）
- 手札のカード：**軽い**カードを出す（破棄・コストの場面が多い）
- トラッシュ／公開ゾーンのカード：**重い**カードを取る（回収・召喚の場面が多い）
- 「〜できる」の発動確認（`confirm`）：80（＝発揮する側に倒す。ここを下げるとAIが何も撃たなくなる）
- スキップ：20（他に選ぶものがないときの最後の逃げ道）

### 「守りを1体は残す」だけは補正が大きい理由

アタックしたスピリットは疲労してブロックに回れない。1手だけを見る評価ではそれが見えず、
両者が全員で殴り合って **平均5.0ターンで決着**していた（2026-08-23 の自己対戦30試合）。
「この体で殴ると回復状態の味方が0になり、相手に回復状態のスピリットがいて、相手ライフが2以上」
のとき −130 する補正を入れて平均6.0ターンになった。
今ターンで削り切れる見込み（相手ライフ1）のときは温存しない。

## 4. 安全弁（`runner.ts`）

| 仕掛け | 目的 |
| :-- | :-- |
| `pumping`（WeakSet） | 同じ対戦でループが二重に走らない。人間の action と AI 自身の action の両方から `pumpAi` が呼ばれるため |
| 弾かれた手を覚える | サーバーに拒否された手を避けて選び直す（同じ手を選び続けて止まるのを防ぐ）。8回続けて拒否されたら降参して対戦を終える |
| `MAX_ACTIONS_PER_PUMP`（400手） | 「打っても盤面が進まない手」を選び続けたときにサーバーを回し続けない |
| `isActive()` | 相手が切断してルームが破棄されたら止まる |

`AI_STEP_DELAY_MS`（既定450ms）が1手ごとの間隔。**`BS_AI_DELAY_MS` で上書きできる**
（E2E は 0 で回す）。

## 5. 既知の限界

直すときはここから。**いずれも「弱い」だけで、対戦が壊れるものではない**。

- **先読みがない**。打った後の盤面を評価していないので、コンボや複数体での詰めは組めない。
  状態を複製して1手先を読む案は見送った（効果解決の副作用まで正しく巻き戻せる保証がないため）
- **マジックの効果の中身を読まない**。撃てるフラッシュマジックはだいたい撃つので、
  リザーブ0で【覚醒】マジックを撃つような空振りが起きる。効果の意味づけをAIに教える仕組みは無い
- **選択待ちの意味を読まない**。prompt の日本語は解釈せず、候補の持ち主とコストだけで決める
- 平均6ターンで決着する（自己対戦）。人間相手なら妥当な速さだが、盤面を作り合う展開にはなりにくい

## 6. 触るときの手順

1. 点数を変えたら **`npm run smoke:quiet`**（`scripts/smoke/part222.ts` が判断の骨格を押さえている）
2. 挙動の変化を見るなら AI 対 AI の自己対戦を回す。part222 の「AI 対 AI の自己対戦」節が雛形。
   全色の組み合わせで回して「詰まり0・例外0」を確認してから入れる
3. 実際の socket 経路は E2E（`scripts/e2e.ts` の「AI戦」節）で見る
