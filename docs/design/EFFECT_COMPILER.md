# 効果文コンパイラの設計図（2026-11-13。未実装）

実装役（Opus）がこの文書だけを読んで作れるように書いた。§6 の作業単位はそのままサブエージェントへ渡せる。
ここに無い判断が要るときは推測せず、§9 の「聞くこと」に足して止まる。

## 1. 何を作るか

カードの効果文（`CardData.effect`）を読んで、効果データ（`CardData.effects`）を出す**決定的な**プログラム（AI を使わない）。使い道は2つ。

| 使い道 | コマンド | 出すもの |
| :-- | :-- | :-- |
| 突き合わせ | `npm run audit:compile` | 全カードについて、コンパイル結果と手書きの `effects` の食い違いの一覧。手書きの間違い探しに使う |
| 下書き | `npm run compile:effects -- <cardId または 弾>` | 新しいカードの `effects` の下書き。読めなかった所は場所と理由つきで残す |

**絶対に守る線：読めない所を推測で埋めない。** 読めた所だけを出し、残りは「読めなかった」として文字位置つきで返す（§5.2 の敷き詰めの検査が機械的に保証する）。
近い形で埋めると「書かなかった効果は全緑をすり抜ける」（CLAUDE.md「重要な罠」）を道具が量産することになる。

### 作らないもの

- エンジン・カードデータ・型（`server/`・`shared/`・`data/cards/`）の変更。コンパイラは `scripts/effect-compiler/` の中だけで完結する
- 手書きデータの自動書き換え。食い違いは一覧に出すだけで、直すのは人が判断する
- 1枚専用の仕組み（1枚でしか使わないアクション33種。`ACTION_UNIFY_PLAN.md` の⑤）。読めなかった所として返ればよい
- 既存の検査（`check-effect-gaps.ts`・`spec-skeleton.ts`）の作り直し。見出しの読み方が重なるが、置き換えは別の作業にする

## 2. 実測（2026-11-13。設計の前提）

| 項目 | 値 |
| :-- | --: |
| 効果文のあるカード | 2,440 枚（効果エントリ 4,610 件） |
| 見出し行 | 4,106 行・248 種類（数字を N に均して数えた） |
| 本文の文 | 5,540 文・2,943 種類（「」の中身・数字・色を均して数えた） |
| 文の型の上位100種で拾える文 | 36.8% |
| 文の型の上位1000種で拾える文 | 64.9% |
| 1回しか出ない文の型 | 2,472 種 |

ここから決まること：

1. **文を丸ごとの型で照合する方式は使わない。** 上位1000種を書いても65%にしかならない。対象の言い回し（「BP5000以下の相手のスピリット1体」）・数・期間・動詞を別々に読んで組み立てる（§4.3）
2. **見出しは定型だが、見出しだけでは効果の種類が決まらない。** 『このスピリットのアタック時』の1見出し1エントリのカード98枚のうち、`triggered/onAttack` は71枚で、残りは本文しだいで `constraint`・`onBattleWin`・`onBattleEnd`・`onBlocked` になる。種類は見出しと本文の両方で決める（§4.4）
3. **見出しとエントリは1対1に並ばない。** 1つの見出しからキーワードと誘発の2件が出る、マジック1節から `lendSelfThisTurn` と `fieldEvent` の2件が出る、などがある。比べるのはカード単位で、エントリの集合どうしにする（§5.1）
4. どこまで読めるかは作ってみないと分からない。だから §7 の段階ごとに測り、**止める基準**を先に決めておく

## 4. どう作るか

### 4.1 全体の流れ

```
効果文
  │ ① blocks     見出しで区切る（Lv・タイミング・『』・【キーワード】・合体・バースト）
  ▼
Block[]
  │ ② clauses    本文を節に切り、節どうしの接続（その後／ことで／さらに…）を決める
  ▼
Clause[]
  │ ③ phrases    節の中を「期間・条件・対象・数・動詞」に分けて読む
  ▼
中間表現（EFFECT_SPEC_RULES §1 の欄）
  │ ④ lower      効果の種類を決め、EffectDef の形にする
  ▼
CompileResult { entries, unparsed }
  │ ⑤ compare    正規化して手書きと突き合わせる（audit のときだけ）
  ▼
報告
```

### 4.2 置き場（1ファイル1概念。設計の3原則の2）

```
scripts/effect-compiler/
  types.ts          §4.6 の型（メインループが最初に書いてコミットする。以後、変えるときはメインループだけ）
  blocks.ts         ① 見出しの読み取り
  clauses.ts        ② 節の切り出しと接続
  phrases/
    target.ts       対象の言い回し → filter・side・数
    amount.ts       数（N体・すべて・〜につき・〜まで）
    duration.ts     期間（このターンの間／このバトルの間／期間の書かれていない『アタック時』）
    condition.ts    条件（〜とき／〜なら／〜間）
  verbs/
    bp.ts destroy.ts draw.ts cores.ts exhaustRefresh.ts return.ts discard.ts summon.ts …（動詞の族ごとに1ファイル）
  continuous.ts     常在の効果（〜として扱う・〜できない・〜を受けない・〜すべてをBP+N）
  lower.ts          ④ 種類の決定と EffectDef への組み立て
  normalize.ts      ⑤ 比べる前の正規化（規則の一覧）
  compare.ts        ⑤ 突き合わせ
  mutate.ts         §5.3 の変異の検査
  cli.ts            2つのコマンドの入口・報告の整形
  rules.md          規則の一覧（自動生成。規則 id・出典・例のカード）
data/compile-baseline.json   突き合わせの結果の基準（§5.5）
scripts/smoke/partN.ts       語句の表のテスト（§5.6）
```

### 4.3 語句を読む部品の形

どの部品も同じ形にする。読めたら値と残りの文字列を返し、読めなければ `null` を返す（例外を投げない・推測しない）。

```ts
type Parsed<T> = { value: T; rest: string; consumed: number; rule: string }
type PhraseParser<T> = (text: string, ctx: ParseContext) => Parsed<T> | null
```

- 節を読む順は固定：**期間 → 条件 → 対象 → 数 → 動詞**（日本語の語順どおり前から削る）。動詞まで読んで `rest` が空（句点だけ）になったら、その節は読めた。**少しでも残ったら節全体を「読めなかった」にする**（部分的に読めた結果を出さない）
- 候補が2つ読めたら（規則が2つ当たったら）「読めなかった」にして理由に両方の規則 id を書く。先に書いた規則を勝たせない
- `ctx` に入れるのは、ブロックの見出しの情報と、同じブロックで前の節までに導入された名詞句（「その」の解決用。EFFECT_SPEC_RULES §2.1.1）だけ。カードの `effects` や他のカードは渡さない

### 4.4 効果の種類の決め方（lower）

見出しと本文の形の組で決める。**表は開発用の弾（§5.7）の手書きデータから機械的に起こす**：見出しと本文の形ごとに手書きの `kind`／`trigger` を数え、1通りに決まる組だけを規則にする。割れる組は、割れる理由（本文のどの語が分けているか）を調べて規則を足すか、読めなかった所として残す。

種（2026-11-13 に数えたもの。見出し1つ・エントリ1つのカード741枚）：

| 見出し | 手書きの種類 |
| :-- | :-- |
| `フラッシュ：`（173） | `magic/flash` 173 |
| 『このスピリットの召喚時』（91）・『このブレイヴの召喚時』（22） | `triggered/onSummon` すべて |
| 『このスピリットの破壊時』（60） | `triggered/onDestroy` 58、`reviveOnDestroy` 2 |
| 『このスピリットのアタック時』（98） | `onAttack` 71、`constraint` 8、`onBattleWin` 6、`onBattleEnd` 4、`onBlocked` 2 ほか |
| 『このスピリットのブロック時』（22） | `onBlock` 20、`onBattleWin` 2 |
| 『このスピリットのバトル時』（12） | `onBattleWin` 5、`onBattleStart` 5、`onBattleEnd` 2 |
| 見出しが Lv だけ（89） | `colorAs` 19、`fieldEvent` 18、`aura` 13、`levelAs` 9、`globalConstraint` 6 ほか |
| 『自分のアタックステップ』（30） | `fieldEvent` 11、`aura` 11 ほか |

### 4.5 規則の書き方

規則は1つずつ、次の4つを持つ値として登録する。出典を書けない規則は足さない（＝手順書に無い読み方は、ユーザーに聞いてから。CLAUDE.md「ゲームルールの解釈は、実装前に設計を示して確認する」）。

```ts
type Rule = {
    id: string            // "target.maxBp" のように 部品.内容
    source: string        // 出典。"EFFECT_SPEC_RULES §2.4" "CONJUNCTION 早見表" "TIMED_EFFECTS §4" など
    example: { cardId: string; text: string }   // この規則で読める実在の文（テストがそのまま使う）
    // 読み取りの本体は部品ごとの形
}
```

`rules.md` は登録された規則から自動で作る。規則の数と出典が一覧できる状態を保つ。

### 4.6 型（`types.ts`。これを最初に固定する）

```ts
import type { EffectDef } from "../../server/src/type"

export type Span = { start: number; end: number }   // CardData.effect の文字位置（end は含まない）

export type Block = {
    span: Span                      // 見出しから次の見出しの手前まで
    header: Span | null
    levels: number[] | null         // 見出しに Lv が無ければ null
    timing: "main" | "flash" | null // マジックの「メイン：」「フラッシュ：」
    heading: string | null          // 『』の中身
    keywords: { name: string; param: string | null; span: Span }[]   // 【強襲：2】→ name "強襲", param "2"
    whileCombined: boolean          // 【合体時】【合体中】
    burst: string | null            // 【バースト：…】の条件
    body: Span
}

export type Link = "then" | "also" | "ifResolved" | "pay" | "afterEffect" | "while" | null  // EFFECT_SPEC_RULES §2.3
export type Clause = { span: Span; text: string; linkToPrev: Link }

export type Unparsed = { span: Span; text: string; reason: string }   // reason は人が読む日本語。当たりかけた規則 id があれば書く
export type Ignored = { span: Span; why: "reminder" | "blank" }      // （）の注釈文・空行。効果を持たない

export type CompiledEntry = {
    effect: Omit<EffectDef, "id">   // id は cli が cardId-eN で振る
    spans: Span[]                   // この1件の根拠になった文字位置
    rules: string[]                 // 使った規則 id
}

export type CompileResult = {
    cardId: string
    entries: CompiledEntry[]
    unparsed: Unparsed[]
    ignored: Ignored[]
}

export function compileCard(card: { cardId: string; type: string; effect: string }): CompileResult
```

`compileCard` に渡すのは `cardId`・`type`（spirit／magic／nexus／brave）・`effect` だけにする。`effects` を渡せない形にしておくことで、手書きの写しになるのを型で防ぐ。

## 5. どうやって正しいと示すか

「テストが通った」では足りない（テストは作った本人の読み方の写しになる）。次の7つを全部そろえる。

### 5.1 手書きデータとの突き合わせ（正解は既にある）

カードごとに、コンパイル結果のエントリと手書きのエントリを正規化（§5.1.1）して、**完全に一致するものどうしを対にする**（順番は見ない）。

| 残り方 | 呼び名 | 意味 |
| :-- | :-- | :-- |
| 対になった | 一致 | ― |
| コンパイラ側だけに残った | **食い違い** | コンパイラの規則が間違っている、または手書きが間違っている |
| 手書き側だけに残り、そのカードに「読めなかった所」がある | 未対応 | 想定どおり。数えるだけ |
| 手書き側だけに残り、「読めなかった所」が無い | **食い違い** | 効果文に無いものが手書きにある、またはコンパイラが黙って落とした |

出す数字は2つ。**大事なのは正しさのほうで、読めた割合は高くなくてよい。**

- **正しさ** ＝ 一致 ÷ コンパイラが出したエントリ数
- **読めた割合** ＝ 全エントリが一致し「読めなかった所」も無いカード ÷ 効果文のあるカード

**食い違いは1件ずつ、3つのどれかに仕分けて理由を書く**（`data/compile-baseline.json` の `triage`）：

1. コンパイラの間違い → 直す。残さない
2. 手書きの間違い → issue を立てる（Muse の【監査】と同じ流れ）。直るまで基準に issue 番号つきで残す
3. 書き方が違うだけで同じ意味 → 正規化の規則を足す（§5.1.1 の条件を満たすときだけ）。満たせなければ「同じ意味と判断した理由」を書いて基準に残す

仕分けの済んでいない食い違いが1件でもあれば、その段階は終わっていない。

#### 5.1.1 正規化の規則

`normalize.ts` に一覧として持ち、1つずつ「なぜ同じ意味と言えるか」をハンドラの該当行で示す。足してよいのは次の2種類だけ。

- 比べない欄：`id`
- 既定値の省略：ハンドラが「無いときはこの値」と読んでいることを確かめられた欄（例：`optional: false`）

`sequence` の入れ子の平坦化のような**構造の書き換えは正規化に入れない**（同じ意味かどうかが解決順に依存するため）。

### 5.2 敷き詰めの検査（黙って落とさないことの保証）

全カードについて、`entries[].spans`・`unparsed[].span`・`ignored[].span` を合わせると **効果文の全文字がちょうど1回ずつ覆われる**ことを検査する（重なりも隙間も失敗）。
これが「読めた所と読めなかった所のほかに、消えた文字が無い」の証明になる。`ignored` にできるのは（）で囲まれた注釈文と空行だけで、その判定も規則として登録する。

### 5.3 変異の検査（突き合わせが甘くないことの証明）

一致したエントリの手書き側を機械的に1か所だけ壊し、突き合わせが**食い違いとして検出する**ことを確かめる。壊し方：

- 陣営を逆にする（own ↔ opponent）／数を±1する／`duration` の turn ↔ battle／`levels` を1つ減らす／`optional` を逆にする／`target: "self"` を外す・付ける／`filter` の欄を1つ消す

検出できなかった変異は、正規化がその欄を捨てているという意味なので、正規化を直す。**検出率100%**（検出できない変異が残るなら、その欄と理由を一覧に書く）。

加えて、実際にあった間違いを戻して検出できることを確かめる（少なくとも次の3つ。PR 番号から直す前のデータを取る）：

| 間違い | 直した PR |
| :-- | :-- |
| 期間の書かれていない『アタック時』の付与が turn になっていた（光輝の勇者皇リュート） | #489 |
| 「そのスピリット」の指す先が発生源とイベントの対象で入れ違っていた（BS13-X04。TEST_STRATEGY の受け入れ確認と同じデータ） | #229 |
| 見出しの『自分のメインステップ』などの限定がデータに無く、時間帯の外でも働いた | #369 |

対象のカードがまだ読めない段階では、読めるようになった段階でこの確認を足す。

### 5.4 形の検査

- `lower.ts` の戻り値は `EffectDef` 型なので、存在しない欄・値は型検査で落ちる（手書きの JSON は型検査の外だが、コンパイラの出力は中に入る）
- コンパイル結果を `validateCards` に通し、問題0件

### 5.5 基準ファイルと後戻りの検出

`data/compile-baseline.json` にカードごとの状態（一致／未対応／食い違いと仕分け）を持つ。`npm run audit:compile -- --check` は、**一致だったカードが一致でなくなったら落ちる**。
コンパイラを直したときの後戻りと、カードデータを書き換えて効果文と合わなくなったことの両方が出る。増えた一致は `--update` で基準に入れる。

最初は定型の検証（CI）に入れない。型の統一の移行をするとデータの書き方が変わり、コンパイラの `lower` も同時に直す必要が出るため。入れるかどうかは §7 の M3 のあとで決める（§9-3）。

### 5.6 語句の表のテスト（作った本人に書かせない）

部品ごとに「文字列 → 期待する値」の表を smoke の part として書く。**期待値は実装役と別のエージェントが、効果文と手順書だけを見て書く**（CLAUDE.md の3役と同じ理由）。
表の各行は実在のカードの文から取り、cardId を添える。規則の `example` は全部このテストに入る。

### 5.7 開発用と確認用にカードを分ける（当てはめすぎの検出）

| 組 | 弾 | 枚数（効果文あり） | 使い方 |
| :-- | :-- | --: | :-- |
| 開発用 | BS01〜BS15・SD01〜SD06・STARTER | 1,623 | 規則を作るときに読んでよい |
| 確認用 | BS16〜BS23・PROMO・X13・CP13 | 817 | **実装役は読まない。** 段階の終わりにメインループが測るだけ |

開発用と確認用で「正しさ」に大きな差が出たら、開発用のカードに当てはめただけの規則がある。新しい弾で使えるかどうかは確認用の数字で判断する。
確認用で見つかった食い違いは、メインループが文の形だけを一般化して実装役に伝える（カードそのものは見せない）。

## 6. 作業単位（サブエージェントに渡す単位）

`types.ts` はメインループが §4.6 のとおりに書いて先にコミットする。以下は編集するファイルが重ならない。
