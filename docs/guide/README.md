# 保守の手引き

このリポジトリを自分で保守・拡張していくための入口。
**目的から引く索引**として使う（頭から全部読む必要はない）。

---

## この4冊

| 文書 | 何が書いてあるか | いつ読むか |
| :-- | :-- | :-- |
| [ARCHITECTURE.md](./ARCHITECTURE.md) | コードの地図。1つの操作が流れる道筋、ディレクトリの役割、3層設計、中断と再開 | **最初に読む**。以後は迷ったとき |
| [ADDING_CARDS.md](./ADDING_CARDS.md) | カードの追加手順。Wiki からの取り込み、スキーマ、効果文の分解 | 弾を足すとき・1枚直すとき |
| [EFFECT_RECIPES.md](./EFFECT_RECIPES.md) | 効果の実装。既存語彙の探し方、`kind` の選び方、テストの書き方 | 効果を書くとき |
| [MAINTENANCE.md](./MAINTENANCE.md) | 動かす・調べる・出す。検査ツールの使い分け、詰まったときの手順 | 日々 |

---

## まず手を動かすなら

```bash
npm run dev                              # 起動（ブラウザのタブ2つで対戦できる）
npx tsx tools/analyze.ts                 # コードの構造マップを生成
open tools/graph.html                    # 依存関係と呼び出し関係を眺める
npm run gaps:report                      # 残っている実装漏れの全体像
```

構造マップで全体を眺めてから [ARCHITECTURE.md](./ARCHITECTURE.md) を読むと位置関係が掴みやすい。

## このリポジトリで繰り返し起きてきた事故

同じ罠を踏み直さないための一覧。詳細は各文書に書いた。

| 事故 | 対策 |
| :-- | :-- |
| **効果を書き忘れても全緑を通る**（カードデータは型検査の対象外） | `npm run validate:gaps` を必ず回す |
| **キーワードを1件書いて実装済みに見える**（続きの効果が落ちる） | 効果文を1節ずつ列挙して対応を確認する |
| **cardId のハードコードがIDのズレで壊れた** | IDを書くときは機械的に検証する。名前で引く |
| **バグを仕様として固定したテスト**が書かれた | 効果文と照らして正しいと言えることだけを assert する |
| **推測でルールを実装して全緑になった** | 手順の一次資料（`docs/design/`）を先に読む。無ければ決めて書き足す |
| **`git add -A` で他人の削除を復活させた** | 触ったファイルを明示してコミットする |
| **多色カードで色判定が壊れた** | `shared/rules.ts` の述語を通す |

## 引き継ぎのメモ

これまでの開発は Claude への委譲を前提とした体制（`CLAUDE.md`）で進めてきた。
自分で保守する場合、`CLAUDE.md` のうち**委譲・トークン規律の章は読まなくてよい**。
一方、次の3つは体制に関係なく効くので残しておく価値がある。

1. **検証コマンドの定型**（バッチ完了時の1行）
2. **ルールの解釈は推測しない**（実装前に一次資料・決めたら書き足す）
3. **カードデータの罠**（型検査の対象外・cardId のハードコード禁止）

UI（`public/`）は別クローンで並行作業する体制だった。1人で保守するなら制約は無くなるが、
`public/src/deck.ts` などクライアント側にも**サーバーと重複する判定**があるので、
片方だけ直すとズレる（→ `ARCHITECTURE.md` §5）。
