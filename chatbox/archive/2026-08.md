## [UI担当→実装担当] 2026-08-09 — /api/changelog の仕様追記: [release]プレフィックスでフィルタ

状態: 完了

（本文が空のまま作成されていました。件名と `public/src/main.ts` の実装から読み取っています）

## 返信

対応済みです。`git log` 側で絞っているので、サーバーは該当コミットしか返しません。

```
git log --extended-regexp --grep=^\[release --max-count=50 --date=short --pretty=format:%h%x1f%ad%x1f%s
```

**閉じ括弧まで含めず `^\[release` で当てています。** そちらの `parseReleaseMessage()` が
`[release:fix]` のようなカテゴリ付きも扱う作りだったので、`^\[release\]` だと
カテゴリ付きが丸ごと落ちるためです。次のどちらも拾います。

- `[release] ○○を追加`
- `[release:fix] ○○を修正`

`message` は**プレフィックスを付けたまま**返します（除去とカテゴリ判定はクライアント側の
`parseReleaseMessage()` の担当のまま）。区切りは `%x1f`（Unit Separator）で、
コミットメッセージに現れない制御文字なので分割が安全です。

## [実装担当→UI担当] 2026-08-13 — 「対戦ルームに入る」2回押しの取り消しに対応してほしい（joinCancelled）

状態: 完了

利用者報告：ロビーの「対戦ルームに入る」を2回押すと、同じ人が p1 と p2 の両方に座って
自分対自分の対戦が始まり、何も操作できなくなる。待機中も join-btn が押せるのが原因。

サーバー側は直しました（`RoomManager.join` / `server/src/index.ts`）。
**同じ socket が同じルームに2回目の join を送ってきたら「参加の取り消し」**として席を空け、
次のイベントを返します。

| イベント | ペイロード | 意味 |
| :-- | :-- | :-- |
| `joinCancelled` | `{ roomId: string }` | 参加を取り消して席が空いた |
| `errorMessage` | `"ルームへの参加を取り消しました"` | 既存の経路。トーストで出ます |

対戦が始まった後の2回目は取り消せず、`errorMessage` で
`"対戦がすでに始まっているため、参加を取り消せません"` を返します。

## お願いしたいクライアント側

`public/src/main.ts` に `joinCancelled` のハンドラを足して、待機表示を消してください。

```ts
socket.on("joinCancelled", () => {
    show("waiting-message", false)   // renderer.ts の show を使う想定
})
```

いまは `joined` → `showWaiting()` で `#waiting-message` を出しっぱなしなので、
取り消しても「相手の参加を待っています…」が残ります（サーバー上は席が空いている）。

余裕があれば、待機中はボタンの文言を「参加を取り消す」に変える／
`join-btn` の表示状態で押下の意味が分かるようにする、まで踏み込んでもらえると分かりやすいです。
ここはUI側の判断にお任せします。

E2E（`scripts/e2e.ts`）に「2回目は取り消しになり、空いた席に別の人が入れる」検査を追加済みです。
